# Phase 1+2 — `ebc_db` package: schema + persistence primitives

## Context

Doc #8 (`docs/backlogs/8.PROTOBUF_STORAGE_MIGRATION.md`) defines the target
architecture: replace ObjectBox (`ebalistyka_db`) with a single protobuf
document (`Db`) that **is** the app's global state in memory, persisted to
disk only for durability — modeled on `o-murphy/a7p`'s `dart/` package
(protobuf + JSON Schema, MD5-hash-prefixed file format). Package layout and
the `ui_key`-for-addressing question are already decided (new
`packages/ebc_db`, retiring `ebalistyka_db` later; client-generated UUID
`ui_key` on `Profile`/`Ammo`/`Sight` for routing, no relational meaning).

This slice is **Phase 1 (schema artifacts) + Phase 2 (persistence layer)**
from that doc: a self-contained new package with no changes to the running
app. It doesn't touch `lib/` at all — Riverpod wiring is Phase 3, the
ObjectBox-data migrator is Phase 5, deleting `ebalistyka_db` is Phase 6.
Scoping it this way means it's independently buildable/testable before any
app code depends on it.

Reference implementation being mirrored throughout:
[`o-murphy/a7p` `dart/`](https://github.com/o-murphy/a7p/tree/main/dart) —
`bin/generate_proto.dart` (protoc invocation), `lib/src/a7p_file.dart`
(hash-prefixed encode/decode), `lib/src/a7p_validator.dart` (JSON Schema
validation via hand-written proto→JSON), `lib/src/generated/*.g.dart`
(embedded schema constant).

## Schema (`proto/ebalistyka.proto`)

1:1 port of `packages/ebalistyka_db/lib/src/entities.dart`'s fields, minus
`id`/`owner` on every message, plus `ui_key` (client-generated UUID,
addressing only) on `Profile`/`Ammo`/`Sight`, plus the structural changes
from Doc #8: `Weapon` embedded directly in `Profile` (was `ToOne`), `Ammo`/
`Sight` as `repeated` lists on `Profile` (were ObjectBox boxes referenced by
id) with **list order = active item** (index 0), and `Db.profiles[0]` as
the active profile — no separate id/index field anywhere for "active".

## `schema/ebalistyka.schema.json`

Hand-written JSON Schema counterpart validating the decoded-to-JSON shape
of `Db`, same snake_case property names as the `.proto` (matching
`a7p.schema.json`'s convention) — one `object` definition per message
above, wired together the same way `Db` nests them.

## Persistence primitives (`lib/src/`)

- **`db_file.dart` — `DbFile`**: `encode(Db)` / `decode(Uint8List)`,
  MD5-hex-prefixed wire format, byte-for-byte the same scheme as
  `A7pFile` (`[32-byte ASCII-hex MD5][protobuf bytes]`), just swapping
  `Payload` for `Db`.
- **`db_validator.dart` — `DbValidator`**: `validate(Db)` against the
  embedded schema constant, same shape as `A7pValidator` — hand-written
  `Db → Map<String, dynamic>` conversion (not `writeToJsonMap()`, for the
  same reason a7p avoids it: proto3 JSON mapping is camelCase, the schema
  is written in snake_case).
- **`db_store.dart` — `DbStore`** (new, no a7p equivalent — a7p is a
  single-file-per-profile format, not a long-lived app store):
  - `Future<Db> load({required Db Function() orElseSeed})`: reads the
    store file, `DbFile.decode` + `DbValidator.validate`; on missing file
    or any decode/validation failure, returns `orElseSeed()` (seed data)
    rather than throwing — mirrors today's `dbWasResetProvider` reset-on
    -corruption behavior.
  - `Future<void> save(Db db)`: atomic write — encode, write to
    `<path>.tmp`, flush, rename over the real path (atomic on all target
    platforms' filesystems); rotate the previous good file to `<path>.bak`
    first, so a crash mid-write always leaves either the old file or the
    new one intact, never a torn one.

## Codegen scripts (`bin/`)

- **`generate_proto.dart`**: copy of `a7p`'s script, paths adjusted to
  `packages/ebc_db/proto/ebalistyka.proto` → `lib/src/proto/`.
- **`embed_schema.dart`**: reads `schema/ebalistyka.schema.json`, writes
  `lib/src/generated/ebalistyka_schema.g.dart` with the JSON embedded as a
  Dart string constant (`kEbalistykaSchemaJson`) — same purpose as a7p's
  Python `scripts/compile.py --dart` step, done in pure Dart since this
  package has no Python/JS siblings to share a single script with.

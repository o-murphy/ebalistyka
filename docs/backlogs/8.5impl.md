# Phase 5: Legacy ObjectBox → `profiles.ebcp`/`settings.ebcp` migration

## Context

`docs/backlogs/8.PROTOBUF_STORAGE_MIGRATION.md` Phase 5 is the last big
unstarted piece before `packages/ebalistyka_db` can be deleted (Phase 6):
detect the app's old ObjectBox store (`data.mdb`) at startup, ask the user
to import it, and convert it into the new `ebc_db` format. The user has
already prepared the read-side building blocks in `lib/ob_migrate/`
(`ob_dump_reader_flutter` dependency, `schema.fbs`/`schema.json` generated
from the shipped `objectbox-model.json`, `flatc --dart` output in
`generated/schema.g.dart`, and a stub `ob_migrate.dart` sketching the
`readObjectBoxRecords` walk-and-dispatch pattern).

**Hard constraint (explicit from the user): every new file for this
feature lives inside `lib/ob_migrate/`.** The only file outside it that
changes is `lib/main.dart` — one import, one async check, one ternary in
the `runApp()` call. Nothing touches `lib/router.dart` (no new `GoRoute`),
nothing lives under `lib/features/`/`lib/core/`. This is deliberate: once
migration is no longer needed, `lib/ob_migrate/` gets deleted wholesale,
and the user does not want scattered references elsewhere in the app to
hunt down when that happens. (Importing *from* `lib/ob_migrate/` into
stable app code — `db_provider.dart`'s providers, `ebcp_service.dart`'s
`sanitizeName`, `AppLocalizations` — is fine and encouraged; that's a
one-way dependency that creates no cleanup burden later. Only the reverse
— other code importing *from* `ob_migrate` — is restricted to `main.dart`.)

Key research findings that shape the design:
- **No unit conversions needed anywhere.** Full old-entity ↔ new-proto
  field audit (see below) found every differing field is a pure
  rename/re-nesting/parallel-array-to-repeated-message restructuring.
  `ConvertorsState.pressure`/`.temperature` are mmHg/Fahrenheit on *both*
  old and new sides (confirmed via the new proto's own field comments) —
  the "hPa vs mmHg" mismatch this doc's Phase 5 sketch worried about
  doesn't actually exist.
- **`Zero` isn't an old entity** — it's 15 `zero*`-prefixed fields flat on
  old `Ammo`, mapping 1:1 by dropping the prefix into the new embedded
  `Zero` message.
- **Old `Profile` is already strict `ToOne<Weapon>`/`ToOne<Ammo>`/
  `ToOne<Sight>`** (confirmed via `packages/ebalistyka_db/lib/src/
  entities.dart` and `lib/ob_migrate/schema.fbs`) — one old `Profile` row
  maps to exactly one new `Profile`, no combinatorial expansion (per your
  clarification).
- **Orphaned library items** — old `Owner.weapons`/`.cartridges`/`.sights`
  (`ToMany`, independent of any `Profile`) have no home in the new schema
  (`Profile` embeds weapon+ammo+sight directly, no standalone library).
  Per your decisions: warn the user and offer a JSON export (schema-shaped,
  via `ebc_db`'s existing `weaponToJson`/`ammoToJson`/`sightToJson`) for
  weapons *and* ammo *and* sights alike — nothing is silently dropped, and
  what to do with the export is deferred.
- **All `ToOne` relations decode as plain int-id fields already inside each
  record's FlatBuffers table** (`Profile.weaponId`/`.sightId`/`.ammoId`,
  `Owner.activeProfileId`) — confirmed via `schema.fbs`/`schema.g.dart`.
  `ob_dump_reader`'s `readToManyTargets` (for `ToMany`) is not needed at
  all — the orphan calculation is just "library item id not referenced by
  any successfully-migrated `Profile`," computed from data already in hand.
- **Android is empirically verified at the package level, not yet at the
  feature level.** `ob_dump_reader_flutter` 0.1.0-alpha.2 (the exact
  version pinned in this app's `pubspec.yaml`) has a real debug/release
  APK built and run on an Android emulator with a confirmed on-device LMDB
  read/write round-trip across all three ABIs (arm64-v8a, armeabi-v7a,
  x86_64) — see `/home/murphy/flutterproj/ob-dump/flutter/README.md`
  "Verified platforms" and its `CHANGELOG.md`'s `[0.1.0-alpha.2]` entry.
  `ebalistyka/android/app/build.gradle.kts` has no `abiFilters`/ABI
  restriction that would strip the native lib for any of those three. The
  OLD app's ObjectBox `Store` was always opened at
  `getApplicationSupportDirectory().path` directly (no subdirectory, no
  platform branch, confirmed across the entire git history including the
  Android-APK-build commit) — the exact same path `main.dart` already uses
  for `profiles.ebcp`/`settings.ebcp` today, on every platform, so there is
  no path-mismatch risk. What's *not* yet verified is this specific
  feature end-to-end on a real Android build with this app's actual old
  `data.mdb` shape — that's an explicit manual verification step below,
  not something this plan can confirm on its own.
- **Reuse `MyApp`'s existing state pipeline for the actual write** — rather
  than hand-rolling a second `MsgStore` write, the gate widget calls
  `ref.read(profilesProvider.notifier).update((_) => migratedProfiles)`
  and `ref.read(settingsDataProvider.notifier).update((_) => migrated
  Settings)` (both already declared as `ProviderScope` overrides in
  `main.dart` before this widget ever mounts). `ProfilesNotifier.update()`/
  `SettingsDataNotifier.update()` already sanitize (Phase 7's repair gate)
  and persist to `profiles.ebcp`/`settings.ebcp` via the same `MsgStore`
  instances `main.dart` opened — no separate write path to get wrong.

## Decisions confirmed

- **l10n**: real `AppLocalizations` (new keys in `app_en.arb`/`app_uk.arb`),
  not a self-contained string table — consistency with the rest of the app
  wins over the (smaller, acceptable) cleanup cost of a few dead keys once
  `ob_migrate` is eventually deleted.
- **Decline behavior**: re-prompt on every launch until the user either
  migrates or manually deletes `data.mdb`. No "don't ask again" marker for
  decline — only a successful migration writes the completion marker.
- **Orphaned weapons**: same treatment as ammo/sights (warn + include in
  the JSON export), for symmetry.
- **Progress UI**: indeterminate spinner only (doc's own explicit
  fallback — a determinate bar needs a two-pass count-then-process split
  that isn't worth it for a personal-app-sized `data.mdb`).
- **Dangling refs**: an old `Profile` whose `weaponId`/`sightId`/`ammoId`
  doesn't resolve to a decoded record is skipped (counted, not silently
  fabricated with blank data) — defensive, matches this doc's general
  stance against inventing data.

## New files — all under `lib/ob_migrate/`

### `lib/ob_migrate/legacy_migrator.dart`

```dart
class LegacyMigrationResult {
  final List<Profile> profiles;       // ebc_db.Profile, profiles[0] = old active
  final SettingsData settings;        // ebc_db.SettingsData
  final List<Weapon> orphanedWeapons; // ebc_db types
  final List<Ammo> orphanedAmmo;
  final List<Sight> orphanedSights;
  final int skippedProfileCount;      // dangling weapon/ammo/sight refs
}

Future<LegacyMigrationResult> migrateLegacyData(String objectboxDir) async { ... }
```

Single `readObjectBoxRecords` walk (entity ids per the existing `_idToEntity`
map in `ob_migrate.dart`: 1=Ammo, 2=ConvertorsState, 3=GeneralSettings,
4=Owner, 5=Profile, 6=Sight, 7=TablesSettings, 8=UnitSettings, 9=Weapon,
11=ShootingConditions, 12=ReticleSettings) populates `Map<int, schema.X>`
per entity type (keyed by `record.objectId`) plus a `List<schema.Profile>`
and singleton settings records. After the walk: for each old `Profile`,
resolve weapon/ammo/sight by id, skip on any miss, else build one new
`Profile(uuid: Uuid().v4(), name:, weapon:, ammo:, sight:)`, track which
weapon/ammo/sight ids got used, and — if `Owner.activeProfileId` matches —
remember its index to move to slot 0 afterward (mirrors `ebc_db`'s
`setActiveProfileOf` reorder-to-front logic, done inline here since this
list doesn't exist as a `profilesProvider` yet). Orphaned lists are
whatever weapon/ammo/sight ids were never touched.

**Per-type mapping — pattern once, not every field**: each `_mapWeapon`/
`_mapAmmo`/`_mapSight`/`_mapZero`/`_mapGeneralSettings`/etc. is a small
pure function, old `schema.X` (flatc reader, camelCase getters) → new
`ebc_db` proto (built fresh via constructor, not `ensureX()`-mutate, so no
frozen-default pitfall). Three patterns repeat:
1. **Straight rename** (majority of fields — `Weapon`, `Sight`,
   `GeneralSettings`, `TablesSettings`, `UnitSettings`, `ShootingConditions`,
   `ReticleSettings`, all of `Zero`): copy the value across, same unit,
   just old `zeroDistanceMeter` → new `Zero.distanceMeter` (prefix-drop),
   `zeroPressurehPa` → `pressureHPa` (casing only) etc.
2. **Sentinel → optional**: old `Ammo.caliberInch`/`.weightGrain`/
   `.lengthInch`/`.bcG1`/`.bcG7`/`.muzzleVelocityMps` used `-1.0` for
   "unset"; new proto fields are `optional double` — only assign when the
   old value is a real one (`> 0`), leaving the field unset otherwise
   (mirrors how `sanitizeProfile`/the rest of `ebc_db` already treats
   optional numeric fields).
3. **Parallel-array zip → repeated message**: old
   `multiBcTableG1VMps`/`multiBcTableG1Bc` (and the G7/custom-drag/
   powder-sensitivity equivalents) are separate `Float64List?` pairs;
   zip index-by-index into `MultiBcPoint`/`CustomDragPoint`/
   `PowderSensitivityPoint` lists (same target shape Phase 7 already
   built) — skip zipping (and count as a data-quality note, not a hard
   failure) if a pair's two lists have different lengths.
4. **Flat → nested** (`ConvertorsState` only): old is 27 flat fields
   (`lengthValueInch`/`lengthLastUnit`, `anglesConvDistanceValueMeter`,
   `velocityAtmoPressureHPa`, `distanceConvTargetSizeInch`, …); new is
   `UnitValue length/weight/pressure/temperature/torque` (2 fields each)
   plus `AnglesConv`/`VelocityConv`/`DistanceConvTargetSize` sub-messages
   — same 27 values, just grouped, no conversions.

### `lib/ob_migrate/orphaned_export.dart`

```dart
Future<void> shareOrphanedDataJson(
  BuildContext context, {
  required List<Weapon> weapons,
  required List<Ammo> ammo,
  required List<Sight> sights,
}) async { ... }
```

Builds `{"weapons": [...], "ammo": [...], "sights": [...]}` via `ebc_db`'s
existing `weaponToJson`/`ammoToJson`/`sightToJson` (imported from
`package:ebc_db/src/validation/profiles_json.dart` — package-internal but
not GB path-dependent; these functions are exactly the schema-shaped JSON
the user asked for, reusing them beats re-deriving the mapping by hand),
`jsonEncode`s it, and shares/saves it the same way `EbcpService`/
`A7pService` already do (mobile: `share_plus` + temp dir; desktop:
`FilePicker.saveFile`) — same pattern, just a `.json` file instead of
`.ebcp`/`.a7p`. Reuses `EbcpService.sanitizeName` from
`lib/core/services/ebcp_service.dart` for the filename (an outbound
import from `ob_migrate`, which is fine per the constraint above).

### `lib/ob_migrate/migration_gate_screen.dart`

```dart
class MigrationGate extends ConsumerStatefulWidget {
  const MigrationGate({required this.objectboxDir, required this.child, super.key});
  final String objectboxDir;
  final Widget child; // MyApp(), shown once resolved
}
```

Internal stage enum (`confirm → migrating → orphanedWarning (if any) →
done`, or `confirm → done` on decline). `build()`: while unresolved, its
own minimal `MaterialApp` (needed for `showDialog`/`showConfirmDialog`
inside the flow — reuses `lib/shared/widgets/confirm_dialog.dart`'s
`showConfirmDialog`) wrapping a `Scaffold` whose body switches on stage;
once resolved, returns `widget.child` directly — no `Navigator.push`
gymnastics, no double-`MaterialApp`-mounted issue (only one is ever in the
tree, since `build()` fully replaces its own output).

Flow:
1. **Confirm** — `showConfirmDialog` variant: "Found old data — import
   it?" New l10n keys in `app_en.arb`/`app_uk.arb`.
2. **Decline** → resolve to `widget.child` immediately, nothing written,
   nothing marked (re-prompts next launch, per your decision).
3. **Confirm → migrating** — spinner, calls `migrateLegacyData
   (widget.objectboxDir)`. On error: show the error (mirrors this app's
   `debugPrint` + `showFeedback` pattern established for `.ebcp` import),
   offer retry/decline — don't silently continue to Home with a caught
   exception.
4. **On success** — `ref.read(profilesProvider.notifier).update((_) =>
   result.profiles)`, `ref.read(settingsDataProvider.notifier).update((_)
   => result.settings)` (persists via the existing `MsgStore`s
   `main.dart` already opened — see Context). Write the completion marker
   (`File('${widget.objectboxDir}/.ob_migration_done').writeAsBytes([])`)
   so `hasUnmigratedLegacyData` returns false next launch.
5. **If any orphaned weapons/ammo/sights** — one screen: "N weapons, M
   ammo, K sights from your old library weren't part of any profile and
   weren't imported" + an "Export as JSON" button (`shareOrphanedDataJson`)
   + "Continue" button.
6. **Done** → resolves to `widget.child`.

### `lib/ob_migrate/ob_migrate.dart` — becomes the single public entry point

Keeps the existing `_idToEntity` map (reused by `legacy_migrator.dart`'s
walk). Replaces `migrateFuncTemplate()` (superseded by the real
`migrateLegacyData`) with:

```dart
const _migrationDoneMarker = '.ob_migration_done';

Future<bool> hasUnmigratedLegacyData(String appSupportDir) async {
  final dataFile = File('$appSupportDir/data.mdb');
  final marker = File('$appSupportDir/$_migrationDoneMarker');
  return await dataFile.exists() && !await marker.exists();
}
```

(The marker-write itself happens in `migration_gate_screen.dart`'s success
path, since that's the one place that knows migration actually succeeded;
`ob_migrate.dart` just owns the constant + the read-side check, keeping
the marker filename in one place.)

Exports `hasUnmigratedLegacyData` and `MigrationGate` — the only two
symbols `main.dart` needs.

## Shipped — deviations and findings from live testing

Everything above was implemented essentially as planned. Two things
surfaced only once real code ran against real data, recorded here rather
than silently folded into the plan text above:

**Crash found and fixed: wrong `BuildContext` for `AppLocalizations`.**
First `flutter run -d linux` against a real `data.mdb` threw `Null check
operator used on a null value` inside `AppLocalizations.of(context)!`,
both in `_MigrationGateState._confirm` and `_buildBody`. Root cause:
`MigrationGate.build(BuildContext context)`'s `context` parameter (and
`State.context`, used identically) sits *above* the `MaterialApp` that
`build()` itself constructs and returns — neither is a descendant of the
`Localizations` widget that `MaterialApp` provides, since that subtree
doesn't exist yet during `MigrationGate`'s own build. Fix: wrap the
`Scaffold`'s body in a `Builder`, and thread that Builder's inner context
through `_confirm`/`_migrate`/`_buildBody` explicitly instead of ever
using `State.context` for anything Localizations/Navigator-dependent. The
postFrameCallback that triggers the initial confirm dialog also moved
from `initState` (which only ever has the outer, wrong context available)
into that `Builder`, guarded by a `_confirmDialogScheduled` flag so it
fires exactly once per gate lifetime despite the builder re-running on
every `setState`.

**Verified end-to-end on Linux with the developer's real `data.mdb`** (not
just synthetic test data): gate appeared, confirm → spinner → success;
`profiles.ebcp` decoded back out afterward showed one profile
(".338LM UKROP 250GR SMK") with sane weapon/ammo/sight/zero values
(caliber 0.338", 250gr, G7 BC 0.314, MV 888 m/s, zero distance 100m,
pressure 1013 hPa) and `settings.ebcp` showed sane
general/unit/tables/shootingConditions/reticle values. `.ob_migration_done`
was written and confirmed to suppress the gate on next launch.

**Open finding, not yet resolved**: the migrated `ConvertorsState` decoded
as all-zero/empty (`length.value=0.0`, `length.lastUnit=""`, etc.) instead
of the old entity's non-zero defaults (`lengthValueInch = 100.0`, unit
`"inch"`, ...). This means `migrateLegacyData`'s local `convertorsState`
variable was never populated from the walk — i.e. the real `data.mdb`
apparently has **no `ConvertorsState` record at all** (entity id 2 never
seen), which is plausible if the old app only ever created that row
lazily, the first time a user opened a unit-converter screen — not
confirmed either way yet. `_mapConvertorsState(null)` correctly falls back
to proto defaults in that case, so this isn't a decode bug per se, but it
should be confirmed against the user's actual old-app usage (did they ever
use the converter screens?) before being considered fully explained.

**Still open**: Android end-to-end (package-level support is verified,
this app's actual flow is not — see the main doc's Phase 5 section).

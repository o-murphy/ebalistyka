# Phase 3 — Riverpod integration (`ebc_db` wired into the running app)

> **Status: PLANNED, not started.** Superseded plan — see note below.

## Note on this doc's history

An earlier version of this plan (list-based `Profile.ammo`/`.sights`,
target-profile picker for duplicating ammo/sight, `my_ammo_screen.dart`/
`my_sights_screen.dart` becoming profile-scoped) was approved and then
walked back before any Phase 3 code was written. While reasoning through
that plan's consequences (a `duplicateAmmo` needing a separate source/
target profile, the caliber-mismatch check having to specifically *avoid*
touching a shared `weapon` because it could invalidate other ammo in the
same list, "My Ammo"/"My Sights" needing a `profileUiKey` and navigation
restructuring), the user made the call: simplify the schema itself to
**1 profile : 1 weapon : 1 ammo : 1 sight** — no `repeated Ammo`/`repeated
Sight` at all — matching `a7p`'s own shape (one `Payload` → one `Profile`
→ one weapon/cartridge/sight) that this whole migration is modeled on.
Every piece of friction in the old plan was a direct symptom of the list
shape; removing the lists removed the friction along with it. This also
makes the schema more directly compatible with `.ebcp`'s own DTOs
(`ProfileExport`/`AmmoExport`/`SightExport`), which already assume one
ammo/sight per profile — easing the eventual Phase 3.5 port.

**The `.proto`/schema/validator/test simplification described above is
still true** — `Profile` is still 1 weapon : 1 ammo : 1 sight, and every
consequence drawn from that (no `duplicateAmmo`, no "My Ammo"/"My Sights"
screens, safe two-directional caliber-mismatch check, etc.) below is
unaffected by what changed next.

## Update — second revision: storage moved from one `Db` file to two

Doc #8 itself went through a second storage-shape revision *after* the
note above was written, independent of the ammo/sight question: there is
no `Db` message anymore. `packages/ebc_db` now ships three independent
root messages, each with its own `.proto`/schema/validator/codec, 38 tests
passing:

- **`ProfilesData`** (`repeated Profile profiles`, `profiles[0]` still the
  active profile) — persisted to `profiles.ebcp` via `ProfilesFile`
  (codec) + `MsgStore<ProfilesData>` (atomic load/save).
- **`SettingsData`** (the six settings sub-messages) — persisted to
  `settings.ebcp` via `SettingsFile` + `MsgStore<SettingsData>`.
- **`EbcpData`** (`repeated ProfilesData profiles_data`, `optional
  SettingsData settings_data`) — the future share/export envelope, not an
  app-storage file, not touched by this phase (Phase 3.5 still owns the
  `.ebcp` cutover).

Everywhere below that referenced `Db`/`dbProvider`/`db.pb`/`seedDb()`
against the old single-document design now needs two notifiers
(`settingsProvider`/`profilesProvider`) and two files instead of one — see
the rewritten Design section. Nothing about the ammo/sight 1:1:1:1 shape,
the UI flow (no My Ammo/My Sights screens), the caliber-filtered replace
picker, or the delete-confirmation copy changes because of this — those
sections are unchanged from the first revision.

## Context

Doc #8, Phases 1+2, is done: `packages/ebc_db` is a self-contained, tested
package — `ProfilesData`/`SettingsData`/`EbcpData` schemas, a generic
`MsgCodec<T>`/`MsgStore<T>` ("md5+ebcpbuf" — 32-byte MD5 hex + protobuf
bytes, atomic tmp+flush+rename+`.bak` write, configurable debounce), and
per-message
validators (`ProfilesValidator`/`SettingsValidator`/`EbcpValidator`) — that
nothing in `lib/` depends on yet. This phase wires it in: `lib/core/
providers/*` switch from ObjectBox (`packages/ebalistyka_db`) to two
in-memory documents (`SettingsData`, `List<Profile>`), replacing every
`Query.watch()` stream with Riverpod `select()` — verified against the
`protobuf` package source (`GeneratedMessage`/`PbList` both implement
deep, recursive `==`), so a change anywhere in either tree is reliably
detected by any selector whose path passes through it, with no per-field
stream bookkeeping.

Scope decision carried over from the original plan (still applies):
**`.ebcp`/`.a7p` import-export is deferred to Phase 3.5.** `ProfileExport`/
`AmmoExport`/`SightExport`/etc. in `ebalistyka_db` are the shared DTO layer
for both `.ebcp` file-sharing (`my_profiles_screen.dart`) and `.a7p`
profile import (`a7p_converter.dart`, `a7p_service.dart`) — porting them
to `ebc_db` types is real, separate work, made easier now by the 1:1:1:1
match but still not free. For this phase they get a short-lived stub, not
a production release state.

## Design

### `lib/core/providers/db_provider.dart` — rewritten for the two-file split

Two independent `MsgStore`s, two independent `Notifier`s. Neither knows
the other exists — `activeProfileProvider` is the only thing that reads
across both.

```dart
final settingsStoreProvider = Provider<MsgStore<SettingsData>>((ref) {
  throw UnimplementedError('settingsStoreProvider must be overridden with an open MsgStore');
});
final profilesStoreProvider = Provider<MsgStore<ProfilesData>>((ref) {
  throw UnimplementedError('profilesStoreProvider must be overridden with an open MsgStore');
});

final dataWasResetProvider = Provider<bool>((_) => false);

class SettingsNotifier extends Notifier<SettingsData> {
  SettingsNotifier(this._initial);
  final SettingsData _initial;

  @override
  SettingsData build() => _initial;

  SettingsData update(SettingsData Function(SettingsData current) mutate) {
    final next = mutate(state);
    state = next;
    unawaited(ref.read(settingsStoreProvider).save(next));
    return next;
  }
}

class ProfilesNotifier extends Notifier<List<Profile>> {
  ProfilesNotifier(this._initial);
  final List<Profile> _initial;

  @override
  List<Profile> build() => _initial;

  List<Profile> update(List<Profile> Function(List<Profile> current) mutate) {
    final next = mutate(state);
    state = next;
    unawaited(
      ref.read(profilesStoreProvider).save(ProfilesData(profiles: next)),
    );
    return next;
  }
}

final settingsProvider = NotifierProvider<SettingsNotifier, SettingsData>(() {
  throw UnimplementedError('settingsProvider must be overridden with an already-loaded SettingsData');
});
final profilesProvider = NotifierProvider<ProfilesNotifier, List<Profile>>(() {
  throw UnimplementedError('profilesProvider must be overridden with an already-loaded profile list');
});

final activeProfileProvider = Provider<Profile?>(
  (ref) => ref.watch(profilesProvider).firstOrNull,
);

final generalSettingsProvider = Provider<GeneralSettings>(
  (ref) => ref.watch(settingsProvider.select((s) => s.generalSettings)),
);
final unitSettingsProvider = Provider<UnitSettings>(
  (ref) => ref.watch(settingsProvider.select((s) => s.unitSettings)),
);
final tablesSettingsProvider = Provider<TablesSettings>(
  (ref) => ref.watch(settingsProvider.select((s) => s.tablesSettings)),
);
final reticleSettingsProvider = Provider<ReticleSettings>(
  (ref) => ref.watch(settingsProvider.select((s) => s.reticleSettings)),
);
final convertorStateProvider = Provider<ConvertorsState>(
  (ref) => ref.watch(settingsProvider.select((s) => s.convertorsState)),
);
final shootingConditionsProvider = Provider<ShootingConditions>(
  (ref) => ref.watch(settingsProvider.select((s) => s.shootingConditions)),
);
```

`lib/main.dart` — mirrors today's `_openStore`/reset-banner pattern, just
against two files instead of one:

```dart
final appSupport = await getApplicationSupportDirectory();
final settingsFile = File(p.join(appSupport.path, 'settings.ebcp'));
final profilesFile = File(p.join(appSupport.path, 'profiles.ebcp'));
final settingsStore = MsgStore<SettingsData>(
  settingsFile, encode: SettingsFile.encode, decode: SettingsFile.decode,
);
final profilesStore = MsgStore<ProfilesData>(
  profilesFile, encode: ProfilesFile.encode, decode: ProfilesFile.decode,
);

final hadSettingsFile = await settingsFile.exists();
final hadProfilesFile = await profilesFile.exists();
var settingsWasSeeded = false;
var profilesWasSeeded = false;
final initialSettings = await settingsStore.load(orElseSeed: () {
  settingsWasSeeded = true;
  return seedSettings(); // new lib/core/providers/db_seed.dart
});
final initialProfilesData = await profilesStore.load(orElseSeed: () {
  profilesWasSeeded = true;
  return seedProfiles(); // same file
});
// A file existing but failing to decode counts as "reset" for that file;
// a file simply never having existed (truly fresh install) doesn't. Track
// each file's own before/after so one file's corruption can't be blamed
// on the other — the banner ORs the two into one yes/no for the user.
final dataWasReset =
    (hadSettingsFile && settingsWasSeeded) ||
    (hadProfilesFile && profilesWasSeeded);

runApp(ProviderScope(
  overrides: [
    settingsStoreProvider.overrideWithValue(settingsStore),
    profilesStoreProvider.overrideWithValue(profilesStore),
    settingsProvider.overrideWith(() => SettingsNotifier(initialSettings)),
    profilesProvider.overrideWith(
      () => ProfilesNotifier(initialProfilesData.profiles),
    ),
    dataWasResetProvider.overrideWithValue(dataWasReset),
  ],
  child: const MyApp(),
));
```

`_DbResetBanner` in `main.dart` is unchanged except reading
`dataWasResetProvider` instead of `dbWasResetProvider`.

### Settings/convertors/conditions notifiers — not affected by the
### ammo/sight shape, and only trivially affected by the storage split

`settings_provider.dart`, `convertors_notifier.dart`,
`shot_conditions_provider.dart`: keep every existing provider name and
base class; only rewrite internals to route through `settingsProvider`
instead of ObjectBox (was `dbProvider` in the pre-split design — these
notifiers never touched profiles, so the split doesn't otherwise change
them). Drop `_loadOrCreate(owner)` (`SettingsData` is always fully
seeded). `restore(export)` stays stubbed for Phase 3.5.

### `app_state_provider.dart` — simpler than the original plan, not more
### complex, now that ammo/sight are singular

- `AppState` keeps `weapons`/`ammo`/`sights`/`profiles`/`activeProfile`
  field names for backward read-compatibility, but they're trivial
  `.map()` now, not `.expand()` over nested lists:
  ```dart
  class AppState {
    final List<Profile> profiles;
    Profile? get activeProfile => profiles.firstOrNull;
    List<Weapon> get weapons => profiles.map((p) => p.weapon).toList();
    List<Ammo> get ammo => profiles.map((p) => p.ammo).toList();
    List<Sight> get sights => profiles.map((p) => p.sight).toList();
  }
  ```
- `AppStateNotifier extends AsyncNotifier<AppState>` stays; `build()`
  derives from `ref.watch(profilesProvider)` — no more manual
  `Query.watch()` subscriptions. `profilesProvider` now backs directly onto
  `ProfilesData.profiles` via `ProfilesNotifier` (see `db_provider.dart`
  above) instead of `dbProvider.select((db) => db.profiles)` — the CRUD
  methods below all end up calling `ref.read(profilesProvider.notifier)
  .update(...)`, which persists only `profiles.ebcp`, never touching
  `settings.ebcp`.
- CRUD addresses profiles by `String uuid` (the only entity that still
  has one): `deleteProfile(String uuid)`, `renameProfile(String uuid,
  String name)`, `duplicateProfile(String uuid, String newName)` (copies
  weapon+ammo+sight together — this is now the *only* "give me a similar
  setup" mechanism, replacing the old per-item duplicate-with-picker idea
  entirely), `setActiveProfile(String uuid)` — moves that profile to
  index 0 of the list (`profiles[0]` = active is still the convention,
  see Doc #8's Open Questions on the still-unresolved reordering-vs.-
  active-index question if manual display-order reordering is ever added).
- **New: `setProfileWeapon`/`setProfileAmmo`/`setProfileSight(String
  profileUuid, Weapon|Ammo|Sight value)`** — replace exactly that one
  field on an existing profile, leaving the other two untouched. Used both
  right after profile creation (pick/build the initial weapon, then ammo,
  then sight) and later for a "replace X" action on an existing profile.
- **No more standalone `duplicateAmmo`/`duplicateSight`/`deleteAmmo`/
  `deleteSight`.** Ammo/sight have no independent existence or identity
  outside their profile — there's nothing to duplicate or delete on its
  own; replacing (`setProfileAmmo`) or deleting the whole profile are the
  only operations that make sense now.
- **Caliber-mismatch check is safe to offer both directions again.** The
  restriction from the old (list-based) plan — "only fix the cartridge,
  never the weapon, because changing the weapon could invalidate other
  ammo in the same profile's list" — no longer applies: a profile has
  exactly one ammo, so updating either side is safe again. Reuse the
  existing dialog (`my_ammo_screen.dart`'s current logic, ~line 253-290)
  unmodified in spirit, just re-triggered by `setProfileWeapon`/
  `setProfileAmmo` instead of a list-attach action.
- `_seed()` moves to `lib/core/providers/db_seed.dart` as two functions,
  `SettingsData seedSettings()` and `ProfilesData seedProfiles()` (one
  file, two top-level functions — there's no single whole-app seed anymore
  since there's no single whole-app document) — `seedProfiles()` returns
  one seeded profile with a default weapon+ammo+sight, matching today's
  seed data; `seedSettings()` returns today's default settings.
- `importProfile`/`importAmmo`/`importSight` (take `ebalistyka_db`
  `*Export` types): stub for this phase — Phase 3.5.

### UI: no more "My Ammo"/"My Sights" library screens at all

Confirmed with the user — the flow is: **create a profile** (wizard or
built-in weapon collection) → **pick or build its ammo** (built-in
cartridge/bullet collection, or the ammo wizard) → **pick or build its
sight** (built-in sight collection, or the sight wizard). An existing
profile gets **"Replace weapon"/"Replace ammo"/"Replace sight"** actions
that reuse the exact same collection-or-wizard choice. This is already
exactly how weapon selection works today for a *new* profile
(`my_profiles_screen.dart`'s "Create new" vs. "From collection" action
sheet, `Routes.profileAddWeaponCreate`/`profileAddWeaponCollection`) — this
phase generalizes that one pattern to ammo and sight, and to existing
profiles, instead of introducing a different pattern (a shared library
screen) for them.

- **Delete** `lib/features/home/sub_screens/my_ammo_screen.dart` and
  `my_sights_screen.dart` outright (not adapt — they have no role left).
- **Router** (`lib/router.dart`): the `ammo-select`/`sight-select` branches
  currently point at `MyAmmoScreen`/`MySightsCollectionScreen`. Repoint
  them at the same action-sheet pattern `weapon-create`/`weapon-collection`
  already use — landing directly on `AmmoWizardScreen`/`AmmoCollectionScreen`
  or `SightWizardScreen`/`SightCollectionScreen` respectively, no
  intermediate library screen. These routes serve both "picking for a new
  profile" and "replace on an existing profile" — same destination, the
  caller just does something different with the returned value.
- **`HelpData.myAmmoScreen`/`mySightsScreen`** (`help_dialog.dart`) and
  `assets/markdown/{en,uk}/myAmmoScreen.md`/`mySightsScreen.md`: delete,
  don't rewrite — the screens they document no longer exist.
- **`assets/markdown/{en,uk}/profilesScreen.md`**: update to describe the
  new inline pick-or-build flow for weapon/ammo/sight, and the "Replace
  weapon/ammo/sight" actions on an existing profile.

### "Replace weapon" (and now ammo/sight) picker, filtered by caliber

Still needed, same reasoning as before: today `WeaponCollectionScreen` is
only reachable from *create new profile*; there's no way to replace the
weapon (or, now, ammo/sight) on a profile that already exists.
`filter_providers.dart`'s `WeaponFilterState`/`WeaponFilterNotifier`
currently only filter by `vendors`, unlike `AmmoFilterState` which already
has `calibers` + an `AmmoFilterNotifier(_defaultCaliberInch)` constructor
that pre-seeds from a caliber. Simpler than the old (list-based) version
of this plan: since `Profile.ammo` is now a single value, the default seed
is exactly one `double?` (that profile's one ammo's caliber), the same
shape `AmmoFilterNotifier` already uses — no `Set<double>` of "calibers
present across a list" needed.

- Add `calibers`/`toggleCaliber` to `WeaponFilterState`/
  `WeaponFilterNotifier`, mirroring `AmmoFilterState` exactly.
- `weaponCollectionFilterProvider` becomes a
  `NotifierProvider.autoDispose.family<WeaponFilterNotifier,
  WeaponFilterState, double?>` — same family-key shape as
  `ammoFilterProvider`.
- New actions on an existing profile in `my_profiles_screen.dart`:
  "Replace weapon" (pre-filtered by that profile's ammo caliber), "Replace
  ammo", "Replace sight" — each pushes the relevant collection/wizard
  choice and calls `setProfileWeapon`/`setProfileAmmo`/`setProfileSight`
  with the result.

### Delete-profile confirmation copy

Same finding as the original plan, still applies: `removeProfileContent`
in `lib/l10n/app_en.arb`/`app_uk.arb` — *"Remove "{name}" and its
weapon?"* / *"Видалити "{name}" та відповідну зброю?"* — needs to say
weapon **and** ammo **and** sight are all deleted (now unconditionally
true, not "only if unreferenced elsewhere" — a profile fully owns all
three). Update both `.arb` entries and regenerate.

## Verification

1. `flutter analyze` — no compile errors after the rewrite.
2. Cold start, neither `settings.ebcp` nor `profiles.ebcp` exists yet →
   `seedSettings()`/`seedProfiles()` both run, home screen shows the
   seeded profile.
3. Create a profile: pick/build weapon, then ammo, then sight — all three
   inline, no separate library screen visited. Verify only `profiles.ebcp`
   is rewritten (e.g. mtime/hash check), `settings.ebcp` untouched.
4. On an existing profile: "Replace ammo" → caliber-filtered picker (or
   wizard) → only `ammo` changes, `weapon`/`sight` untouched. Same for
   "Replace weapon"/"Replace sight".
5. Edit a setting (theme, unit) → UI updates immediately; restart app →
   persisted; verify only `settings.ebcp` was rewritten.
6. Delete a profile → confirmation mentions weapon+ammo+sight; all three
   gone after confirming.
7. Corrupt `profiles.ebcp` only (leave `settings.ebcp` intact), restart →
   reset banner shows, seeded profile list loads, but the settings changed
   in step 5 are still there (the two files reset independently). Repeat
   corrupting `settings.ebcp` only, confirm the reverse.
8. Select a different profile → `profiles.ebcp` rewritten with that
   profile at index 0; restart app → same selection persists.
9. `.ebcp` share/import entry points show a clear "not yet available"
   state rather than crashing.

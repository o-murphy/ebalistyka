# Phase 3 — Riverpod integration (`ebc_db` wired into the running app)

## Context

Doc #8 (`docs/backlogs/8.PROTOBUF_STORAGE_MIGRATION.md`), Phases 1+2, is
done: `packages/ebc_db` is a self-contained, tested package (schema,
`DbFile`, `DbValidator`, `DbStore` with configurable debounce) that nothing
in `lib/` depends on yet. This phase wires it in: `lib/core/providers/*`
switch from ObjectBox (`packages/ebalistyka_db`) to `ebc_db`'s single
in-memory `Db` document, replacing every `Query.watch()` stream with
Riverpod `select()` — verified against the `protobuf` package source
(`GeneratedMessage`/`PbList` both implement deep, recursive `==`), so a
change anywhere in the tree is reliably detected by any selector whose path
passes through it, with no per-field stream bookkeeping.

Two scope decisions made while researching this phase, both because they
turned out to be bigger than "just" Riverpod wiring:

1. **`.ebcp`/`.a7p` import-export is deferred to Phase 3.5.** `ProfileExport`/
   `AmmoExport`/`SightExport`/etc. in `ebalistyka_db` are the shared DTO
   layer for *both* `.ebcp` file-sharing (`my_profiles_screen.dart` etc.)
   *and* `.a7p` profile import (`a7p_converter.dart`, `a7p_service.dart`) —
   porting them to `ebc_db` types is real, separate work. For this phase
   they get a short-lived stub (see below); not a production release state.
2. **No `ammo_library`/`sight_library` in `Db`; "My Ammo"/"My Sights" become
   children of a profile, not top-level shared screens.** Today
   `AppState.ammo`/`.sights` are global ObjectBox boxes an `Ammo`/`Sight`
   can be `ToOne`-referenced from multiple profiles at once — that's how
   these screens work as app-wide shared libraries today, and how editing
   one entry can ripple into every profile that references it. Doc #8's
   schema has no cross-refs — `Profile.ammo`/`.sights` are each profile's
   own embedded copies. Confirmed with the user: this is intentional under
   the new model — the screens move from the main menu to being scoped to
   one profile (need a `profileUiKey` to know which profile's list they're
   showing), and editing an entry only ever touches that one profile's own
   copy. Adding "the same" ammo to two profiles means two independent
   copies from the start, not a shared reference. No `.proto` changes
   needed for this.

## Design

### `lib/core/providers/db_provider.dart` — rewritten

```dart
final dbStoreProvider = Provider<DbStore>((ref) {
  throw UnimplementedError('dbStoreProvider must be overridden with an open DbStore');
});

final dbWasResetProvider = Provider<bool>((_) => false);

class DbNotifier extends Notifier<Db> {
  DbNotifier(this._initial);
  final Db _initial;

  @override
  Db build() => _initial;

  /// The one path every mutation goes through. [mutate] gets the current
  /// Db and returns a new one (protobuf `rebuild()`/deep-copy) — `state =`
  /// is only ever assigned once per call, so there's no observable
  /// half-mutated state (replaces every `runInTransaction` block today).
  Db update(Db Function(Db current) mutate) {
    final next = mutate(state);
    state = next;
    unawaited(ref.read(dbStoreProvider).save(next));
    return next;
  }
}

final dbProvider = NotifierProvider<DbNotifier, Db>(() {
  throw UnimplementedError('dbProvider must be overridden with an already-loaded Db');
});

// One Provider<T> per top-level Db field — this is where "global broadcast,
// subscriber picks what it needs" actually lives: each of these memoizes
// on Db's deep equality, so a change to `db.unitSettings` never re-notifies
// `generalSettingsProvider`'s watchers.
final generalSettingsProvider = Provider<GeneralSettings>(
  (ref) => ref.watch(dbProvider.select((db) => db.generalSettings)),
);
final unitSettingsProvider = Provider<UnitSettings>(
  (ref) => ref.watch(dbProvider.select((db) => db.unitSettings)),
);
final tablesSettingsProvider = Provider<TablesSettings>(
  (ref) => ref.watch(dbProvider.select((db) => db.tablesSettings)),
);
final reticleSettingsProvider = Provider<ReticleSettings>(
  (ref) => ref.watch(dbProvider.select((db) => db.reticleSettings)),
);
final convertorStateProvider = Provider<ConvertorsState>(
  (ref) => ref.watch(dbProvider.select((db) => db.convertorsState)),
);
final shootingConditionsProvider = Provider<ShootingConditions>(
  (ref) => ref.watch(dbProvider.select((db) => db.shootingConditions)),
);
final profilesProvider = Provider<List<Profile>>(
  (ref) => ref.watch(dbProvider.select((db) => db.profiles)),
);
```

`lib/main.dart` — mirrors today's `_openStore`/reset-banner pattern
exactly, just swapping ObjectBox for `DbStore`:

```dart
final appSupport = await getApplicationSupportDirectory();
final dbFile = File(p.join(appSupport.path, 'db.pb'));
final store = DbStore(dbFile);

final hadFile = await dbFile.exists();
var usedSeed = false;
final initialDb = await store.load(orElseSeed: () {
  usedSeed = true;
  return seedDb(); // new lib/core/providers/db_seed.dart — one seeded Profile
});
final dbWasReset = hadFile && usedSeed;

runApp(ProviderScope(
  overrides: [
    dbStoreProvider.overrideWithValue(store),
    dbProvider.overrideWith(() => DbNotifier(initialDb)),
    dbWasResetProvider.overrideWithValue(dbWasReset),
  ],
  child: const MyApp(),
));
```

`_DbResetBanner` in `main.dart` is unchanged — it only reads
`dbWasResetProvider`.

### Settings/convertors/conditions notifiers — same shape, simpler internals

`settings_provider.dart` (`SettingsNotifier`, `UnitSettingsNotifier`,
`TablesSettingsNotifier`, `ReticleSettingsNotifier`), `convertors_notifier.dart`,
`shot_conditions_provider.dart`: **keep every existing provider name and
base class** (`AsyncNotifierProvider<X, Y>`, sync convenience `Provider<Y>`
wrappers, `themeModeProvider`/`localeProvider`/`appLocalizationsProvider`)
so none of their many UI call sites need to change. Only rewrite what's
*inside*:

- Drop `_loadOrCreate(owner)` entirely — `Db` is always fully populated
  (seeded once, whole-document), so there's no more lazy "create the row if
  missing" step per settings type.
- `build()` becomes `return ref.watch(dbProvider.select((db) => db.generalSettings));`
  (still wrapped in `Future` by `AsyncNotifier` — resolves instantly since
  the source is already synchronous, so `.value` access patterns like
  `themeModeProvider`'s `ref.watch(settingsProvider).value?.flutterThemeMode`
  keep working unchanged).
- Every setter (`setThemeMode`, `updateLengthValue`, `updateDistance`, …)
  becomes one `ref.read(dbProvider.notifier).update((db) => db.rebuild((b) =>
  b.generalSettings.themeMode = ...))` call instead of
  `_store.box<X>().put(...)`.
- `restore(export)` methods: stub for this phase (throws
  `UnimplementedError('restore: pending Phase 3.5')`) — these take an
  `ebalistyka_db` `*Export` type that doesn't exist in the new model yet.

### `app_state_provider.dart` — the one with real shape changes

- `AppState` keeps its field names (`weapons`, `ammo`, `sights`, `profiles`,
  `activeProfile`) so most read call sites (`appState.ammo`, etc.) don't
  change, but `weapons`/`ammo`/`sights` become **computed flattened views**
  over `profiles` instead of independent lists:
  ```dart
  class AppState {
    final List<Profile> profiles;      // ebc_db.Profile
    Profile? get activeProfile => profiles.firstOrNull;
    List<Weapon> get weapons => profiles.map((p) => p.weapon).toList();
    List<Ammo> get ammo => profiles.expand((p) => p.ammo).toList();
    List<Sight> get sights => profiles.expand((p) => p.sights).toList();
  }
  ```
- `AppStateNotifier extends AsyncNotifier<AppState>` stays; `build()`
  derives from `ref.watch(profilesProvider)` (no more manual
  `Query.watch()` subscriptions — Riverpod's own dependency tracking on
  `profilesProvider` replaces the `subs`/`ref.onDispose` block entirely).
- **Every CRUD method's addressing moves from `int id` to `String uiKey`**
  (`ui_key` is the new stable identity — see Doc #8's resolved "entity
  keys" question). `deleteAmmo(int id)` → `deleteAmmo(String profileUiKey,
  String ammoUiKey)`, etc. — every method that used to address a *shared*
  Ammo/Sight/Weapon by id now needs **which profile** it belongs to as
  well, since these are no longer independently-addressable global rows.
- **`duplicateAmmo`/`duplicateSight` take a separate *source* and
  *target* profile** — copying is never implicit/in-place anymore:
  `duplicateAmmo(String sourceProfileUiKey, String ammoUiKey, String
  targetProfileUiKey, String newName)`. The UI must ask *which profile* to
  copy into (a profile picker step) rather than silently duplicating into
  the profile the user was already looking at — duplicating "in place"
  into the same profile is just the picker defaulting to (or the user
  choosing) the current profile, not a distinct code path.
- **The existing caliber-mismatch check must still run against the
  *target* profile, but the "update the weapon's caliber" resolution
  option is removed — only the cartridge can be corrected now.** Found the
  actual check — it's inline in `my_ammo_screen.dart` (~line 253-290):
  compares `item.caliberInch` against the profile's `weapon.caliberInch`
  and, on mismatch, today offers *either* updating the cartridge's caliber
  *or* the weapon's. That comparison must move to run against the
  *target* profile's weapon once duplicate has a target-profile picker
  (which may have a different caliber than the source) — but the
  weapon-side fix must be dropped entirely, not just re-pointed at the new
  target. Reason: `Profile.ammo` is a **list** now (potentially several
  cartridges per profile) — silently changing that profile's one shared
  `weapon.caliberInch` to accommodate the ammo being added/duplicated in
  would invalidate the caliber match for every *other* ammo already in
  that same profile's list, a hidden side effect that didn't exist when
  ammo was effectively one-at-a-time. Going forward this dialog only ever
  offers "update the cartridge's caliber to match the weapon."
- `_seed()` moves out to `lib/core/providers/db_seed.dart` as a
  `Db seedDb()` free function (called from `main.dart`, not from inside the
  notifier) — seeding is now a whole-`Db` concern, not per-notifier.
- `importProfile`/`importAmmo`/`importSight` (take `ebalistyka_db`
  `*Export` types): stub for this phase, same as the settings notifiers'
  `restore()` — real port is Phase 3.5.

### Known consumer files that must change (id/signature ripple)

Grepped and confirmed — exactly these 4 call the CRUD methods whose
signatures change:
- `lib/features/home/profiles_vm.dart`
- `lib/features/home/sub_screens/my_ammo_screen.dart`
- `lib/features/home/sub_screens/my_profiles_screen.dart`
- `lib/features/home/sub_screens/my_sights_screen.dart`

`my_ammo_screen.dart`/`my_sights_screen.dart` need more than a signature
change — they become **children of a specific profile**, not top-level
menu entries. Today they list *all* ammo/sights app-wide and let you attach
an existing shared row to any profile (a shared reference, edits ripple
everywhere it's attached); under the new model there's no shared row to
attach — each screen needs a `profileUiKey` to know *which* profile's
embedded list it's showing/editing, and editing an entry there only ever
touches that one profile's own copy, never any other profile that happens
to have a similarly-named ammo/sight. This is a navigation-structure change
(these screens move from the main menu into a profile's own screen/flow),
not just an internal data-source swap. Their "duplicate" action also gains
a profile-picker step (pick the target profile — defaults to the current
one, but must let the user choose a different one) since duplication is
never an implicit in-place copy anymore. Router has no `:id`-style path
params (confirmed in `router.dart`), so no route-table changes are needed —
navigation already passes objects/keys via constructor args, not URL params.

**Delete-profile confirmation copy must change.** Found the exact string:
`removeProfileContent` in `lib/l10n/app_en.arb`/`app_uk.arb` — currently
*"Remove "{name}" and its weapon?"* / *"Видалити "{name}" та відповідну
зброю?"*. That wording is accurate today only because ammo/sights survive
independently of a deleted profile (only the weapon cascades, and only if
unreferenced elsewhere). Under the new model ammo/sights are embedded in
the profile and always go with it — the confirmation must say so
explicitly (weapon **and** ammo **and** sights are all deleted, no
exceptions), or a user could be surprised that their sight configuration
vanished. Update both `.arb` entries and regenerate
(`flutter gen-l10n`/whatever the project's l10n build step is).

**In-app help docs describe the old model and need rewriting, not just
code.** Confirmed by reading them —
`assets/markdown/{en,uk}/myAmmoScreen.md` and `mySightsScreen.md` open with
*"Your personal cartridge library. Tap the ✓ button to assign a cartridge
to the current profile"* — exactly the shared-library behavior that's
going away. These need real rewrites (both languages) describing the
profile-scoped screen: no more "assign to current profile" (it's already
scoped to one), duplicate asks which profile to copy into, delete only
affects this profile's copy. `assets/markdown/{en,uk}/profilesScreen.md`
should also be checked for delete-behavior wording consistent with the
`removeProfileContent` string change above.

## Verification

1. `flutter analyze` — no compile errors after the rewrite.
2. Cold start, no `db.pb` yet → `seedDb()` runs, home screen shows the
   seeded profile (mirrors today's ObjectBox seed-on-first-run).
3. Edit a setting (theme, unit) → UI updates immediately; restart app →
   persisted (confirms `dbProvider` → `DbStore.save()` → reload round-trip).
4. Create/duplicate/delete ammo, sight, profile via the wizards → reflected
   in `profilesProvider`-derived views without a manual refresh.
5. Corrupt `db.pb` (write garbage bytes), restart → reset banner shows,
   seeded data loads (mirrors today's `_DbResetBanner` flow).
6. `.ebcp` share/import entry points show a clear "not yet available"
   state rather than crashing (stub, not silent failure).

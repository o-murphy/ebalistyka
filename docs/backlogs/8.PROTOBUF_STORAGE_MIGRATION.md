# Protobuf Storage Migration — Replace ObjectBox with Two Embedded Protobuf Files

> **Doc #8 — Status: DRAFT (Phase 1/2/3/4 done, Phase 3.5/5/6/7 not started)**
> Supersedes Doc #3 (`3.OBJECTBOX_MIGRATION.md`) as the storage layer. Doc #3
> stays as historical record of why/how ObjectBox was adopted; this doc
> replaces it as the *current* target architecture. Phase 3's execution
> log and its post-migration bug-fix follow-up (proto3 null-vs-zero data
> gaps that froze wind/twist/elevation calculations) live in
> `8.3impl.md`/`8.3.md`.

> No multi-user / remote-sync support is planned (see Owner-entity removal
> discussion). The new schema has no `Owner`, no relational ids, and no
> `ToOne`/`ToMany`.

## Note on this doc's history

This doc's storage shape went through several iterations before settling.
Earlier drafts considered: one combined `Db` message in a single `db.pb`
file; a `Db`-per-profile-file scheme (`<uuid>.ebcp` per profile under a
`profiles/` directory); and a unified `EbcpFile` envelope where a single
message type carried optional settings and/or profiles. All three were
walked back. **What actually shipped (Phase 1/2) is simpler than any of
those:**

- **Two independent `.proto` files, two independent root messages, no
  shared envelope.** `packages/ebc_db/proto/profiles.proto` (package
  `profiles`) defines `ProfilesData { schema_version; repeated Profile
  profiles; }`. `packages/ebc_db/proto/settings.proto` (package `settings`)
  defines `SettingsData { schema_version; GeneralSettings; UnitSettings;
  TablesSettings; ReticleSettings; ConvertorsState; ShootingConditions; }`.
  Neither imports the other; they don't share a package or a wrapper
  message.
- **Two files on disk, `profiles.ebcp` and `settings.ebcp`**, both using
  the same "md5+ebcpbuf" wire convention (same idea as `.a7p`), but as two
  separate encodings of two separate message types — not two instances of
  one generic envelope.
- **Active profile is still list position — `profiles[0]`, not a UUID
  pointer.** A `Settings.active_profile_uuid` field was drafted and then
  explicitly rejected: the app keeps the original ObjectBox-era convention
  of "the active profile is whichever one is first," now scoped to
  `ProfilesData.profiles` instead of `Db.profiles`. This means the
  reordering-vs.-active-index question from earlier drafts (see Open
  Questions) is still a live open question, not resolved by construction —
  unlike what an explicit-pointer design would have given for free.
- **`.ebcp` is the extension for both files.** `.ebcp` isn't being
  redefined into a single shared envelope format — it's just the file
  extension both `ProfilesData` and `SettingsData` happen to use, since
  both are meant to become sendable/shareable independently later (see
  Open Questions on the relationship to today's ZIP+JSON `.ebcp`, which
  this doc still does not touch).

**Update — a third message type, `EbcpData`, was added on top of this.**
`packages/ebc_db/proto/ebcp.proto` (package `ebcp`) defines `EbcpData {
schema_version; repeated profiles.ProfilesData profiles_data; optional
settings.SettingsData settings_data; }`, importing both `profiles.proto`
and `settings.proto`. This *is* the shared/export envelope the earlier
walked-back `EbcpFile` idea was reaching for — but as a genuinely separate,
optional third layer on top of the two independent storage files, not a
replacement for them: `profiles.ebcp`/`settings.ebcp` (this package's own
on-disk state) stay exactly `ProfilesData`/`SettingsData`, unwrapped.
`EbcpData` is for a *different* file — a shared/exported `.ebcp` — that can
bundle one profile (`profiles_data: [oneProfilesData]`, no
`settings_data`, e.g. "share this profile"), or several plus settings
(`profiles_data: [...]`, `settings_data: set`, e.g. "full backup"), all
still "md5+ebcpbuf", all still `.ebcp`. See Message Schema and
Open Questions below — this defines the *shape*, not the cutover: today's
ZIP+JSON `ebcp_service.dart`/`EbcpFile` DTO is still untouched.

## Context

The app currently persists through ObjectBox (`packages/ebalistyka_db`):
a relational-ish object graph (`Weapon`/`Ammo`/`Sight`/`Profile`/settings
entities) linked via `ToOne<Owner>`/`ToMany` backlinks, queried per-owner,
watched via per-box `Query.watch()` streams (see Doc #3, Doc #4).

Two problems with keeping that shape long-term:

1. **`Owner` is dead weight.** It exists solely to prep for multi-user /
   remote sync, which is not going to be built. Every entity carries an
   unused `ToOne<Owner>` and every query filters by it.
2. **ObjectBox itself is being replaced.** `objectbox-c` is a closed-source
   binary; the project's own [`ob-dump`](https://github.com/o-murphy/ob-dump)
   tool exists specifically to read data back out of an ObjectBox store
   without depending on that binary, precisely so this kind of migration is
   possible later without hostage data.

Rather than doing ObjectBox schema surgery now (drop `Owner`, regenerate
codegen, retire model UIDs) and then throwing that work away when the
storage engine changes, this doc defines the target architecture directly
and treats `Owner` removal as a side effect of the rewrite, not a separate
step.

## Core Design

- **Settings and profiles are two fully independent documents, with
  independent schemas.** Nothing needs the two together at the file or
  message level — settings never reference a profile, profiles never
  reference settings. `ProfilesData` and `SettingsData` are separate proto
  packages, compiled to separate Dart libraries
  (`lib/src/proto/profiles.pb.dart`, `lib/src/proto/settings.pb.dart`),
  with no cross-import between them.
- **Both files share one wire convention, not one message type: "md5+ebcpbuf".**
  `[32-byte MD5 hex string][ebcpbuf payload]`, where "ebcpbuf" is plain
  protobuf bytes of one of this package's messages (`lib/src/msg_codec.dart`'s
  `MsgCodec<T>`), parametrized by whichever message's own
  `writeToBuffer()`/`fromBuffer()` is passed in.
  `ProfilesFile`/`SettingsFile` are one-line-per-method wrappers around a
  `MsgCodec<ProfilesData>`/`MsgCodec<SettingsData>` instance. Persistence
  (`lib/src/msg_store.dart`'s `MsgStore<T>`) is the same story: one generic
  class, instantiated once per file, not two near-duplicate classes.
- **Profiles stay a flat list, in one file.** `repeated Profile profiles`
  inside `profiles.ebcp`. `profiles[0]` is the active profile — same
  convention the ObjectBox-era `Db.profiles` sketch used, just scoped to
  its own file now that settings aren't bundled in with it.
- **No cross-references.** No `ToOne`/`ToMany`, no relational ids. Entities
  that must appear in more than one place (e.g. reusing an ammo config
  across profiles) are **copied**, not shared. This trades storage
  duplication for the elimination of an entire class of bugs (dangling
  refs, orphaned rows, cascade-delete logic) — acceptable because the
  dataset is small (single device, no sync).
- **`Profile` is 1 weapon : 1 ammo : 1 sight — no nested lists at all.**
  Originally sketched with `repeated Ammo`/`repeated Sight` per profile.
  Reconsidered during Phase 3 planning (Doc #8.3): every piece of friction
  hit while designing that phase — a target-profile picker for "duplicate
  ammo into a different profile," the caliber-mismatch check having to
  avoid touching a shared `weapon` because it could invalidate *other* ammo
  in the same list, `my_ammo_screen.dart`/`my_sights_screen.dart` needing a
  `profileUiKey` and becoming profile-scoped sub-screens — was a direct
  symptom of ammo/sight being lists. Simplified to exactly one embedded
  `Weapon`/`Ammo`/`Sight` per `Profile`. Consequences:
  - No `uuid` on `Ammo`/`Sight` — only `Profile` needs one (they're no
    longer independently addressable; there's nothing to pick out of a
    list of one).
  - "Trying a different load on the same rifle" = duplicate the *profile*
    (copies weapon along with it — cheap, ~9 scalar fields) and edit the
    duplicate's ammo.
  - The caliber-mismatch check (weapon vs. ammo, see `my_ammo_screen.dart`)
    is safe to let touch *either* side again — updating the one weapon a
    profile has can't silently break "other ammo in the list," because
    there is no other ammo in the list.
  - No standalone "My Ammo"/"My Sights" library screens. Weapon/ammo/sight
    are picked (from the built-in JSON collection) or created (via wizard)
    *inline*.
- **File persistence is a durability layer, not the primary read/write
  path** — in memory, `SettingsData` and `List<Profile>` (loaded from
  `profiles.ebcp`) *are* the app state; writing either file back out is
  serialization for next cold start, same relationship `.a7p` has to a
  single ballistic profile.

## On-Disk Layout

```
<applicationSupportDirectory>/
  settings.ebcp   — md5+ebcpbuf of one SettingsData
  profiles.ebcp   — md5+ebcpbuf of one ProfilesData (profiles[0] = active)

<user-chosen export path>/
  whatever-name.ebcp   — md5+ebcpbuf of one EbcpData (share/backup, Phase 3.5)
```

- Atomicity is per file: `settings.ebcp` and `profiles.ebcp` each get their
  own tmp-write + flush + rename + `.bak` rotation cycle (`MsgStore`),
  independent of each other. A crash mid-write to one never touches the
  other. Within `profiles.ebcp`, though, every profile is rewritten
  together — editing one profile still means re-encoding the whole list,
  same as `Db.profiles` did before the settings split; the split only
  separates *settings* churn from *profile* churn, not profile-from-profile.
- An `EbcpData` file is not one of the app's two internal state files —
  it's a standalone export a user creates/shares/imports (Phase 3.5). It
  reuses the same `MsgCodec`/`.ebcp` wire convention but lives wherever the
  user saves/receives it, not in `applicationSupportDirectory`.

## Message Schema

Source of truth: `packages/ebc_db/proto/profiles.proto` and
`packages/ebc_db/proto/settings.proto`. Don't hand-sync every field here —
this is a structural sketch, not a copy.

```proto
// profiles.proto — package profiles
message Weapon  { /* same fields as today's ebalistyka_db.Weapon, minus id/owner */ }
message Sight   { /* same fields as today's ebalistyka_db.Sight, minus id/owner */ }
message Zero    { /* embedded in Ammo — zero_* fields grouped, see Doc #8.3 */ }
message Ammo    { /* same fields as today's ebalistyka_db.Ammo, minus id/owner; Zero zero = 22 */ }

message Profile {
  string uuid = 1;   // client-generated UUID, addressing only
  string name = 2;
  Weapon weapon = 3;
  Ammo ammo = 4;
  Sight sight = 5;
}

message ProfilesData {
  uint32 schema_version = 1;
  repeated Profile profiles = 2; // profiles[0] = active profile
}
```

```proto
// settings.proto — package settings
message GeneralSettings     { /* minus id/owner */ }
message TablesSettings      { /* minus id/owner */ }
message UnitSettings        { /* minus id/owner */ }
message ShootingConditions  { /* minus id/owner */ }
message UnitValue           { double value = 1; string last_unit = 2; }
message AnglesConv          { /* see Doc #8.3 for ConvertorsState's per-converter split */ }
message VelocityConv        { /* … */ }
message DistanceConvTargetSize { /* … */ }
message ConvertorsState     { /* UnitValue/AnglesConv/VelocityConv/DistanceConvTargetSize fields */ }
message ReticleSettings     { /* minus id/owner */ }

message SettingsData {
  uint32 schema_version = 1;
  GeneralSettings general_settings = 2;
  UnitSettings unit_settings = 3;
  TablesSettings tables_settings = 4;
  ReticleSettings reticle_settings = 5;
  ConvertorsState convertors_state = 6;
  ShootingConditions shooting_conditions = 7;
}
```

`ProfilesData` and `SettingsData` don't wrap each other or share a package
— each is validated independently (`ProfilesValidator`/`SettingsValidator`
against `schema/profiles.schema.json`/`schema/settings.schema.json`),
mirroring `a7p`'s dual-artifact pattern (protobuf + JSON Schema) once per
storage file.

A third, separate message *does* wrap both — but only for the
share/export layer, not storage:

```proto
// ebcp.proto — package ebcp
import "profiles.proto";
import "settings.proto";

message EbcpData {
  uint32 schema_version = 1;
  repeated profiles.ProfilesData profiles_data = 2;
  optional settings.SettingsData settings_data = 3;
}
```

`schema/ebcp.schema.json` validates one `EbcpData` (`EbcpValidator`), but
its *source* file doesn't redefine `Weapon`/`Profile`/`GeneralSettings`/etc.
— it only defines `EbcpData` itself and `$ref`s `#/$defs/ProfilesData`/
`#/$defs/SettingsData`. `bin/embed_schema.dart` resolves those refs at
embed time by merging in `profiles.schema.json`'s and `settings.schema.json`'s
own `$defs` (see that script's `mergeDefsFrom`/`_mergeExternalDefs`), so
the *embedded* runtime constant (`kEbcpSchemaJson`) is fully self-contained
(no external `$ref` resolver needed at `JsonSchema.create()` time) while
the *source* schema stays a single point of truth — nothing is
hand-duplicated on disk. The proto→JSON conversion functions
(`lib/src/profiles_json.dart`, `lib/src/settings_json.dart`) are shared the
same way: top-level functions, not private to one validator, so
`EbcpValidator` reuses `profilesDataToJson`/`settingsDataToJson` instead of
re-implementing the mapping.

## Runtime Architecture — Replacing ObjectBox's `Query.watch()`

Not yet built (Phase 3). Sketch:

```
appSupportDirProvider   (Provider<Directory>)
    │
    ├── settingsFileProvider (Provider<File> — settings.ebcp)
    │       └── settingsProvider (Notifier<SettingsData>)
    │               │ — build(): MsgStore<SettingsData>(file, encode: SettingsFile.encode,
    │               │   decode: SettingsFile.decode).load(orElseSeed: seedSettings)
    │               │ — update(mutate): state = mutate(state); persist via the same store
    │               └── one select()-based provider per settings sub-field,
    │                   same pattern as today's settings_provider.dart
    │
    └── profilesFileProvider (Provider<File> — profiles.ebcp)
            └── profilesProvider (Notifier<List<Profile>>)
                    │ — build(): MsgStore<ProfilesData>(...).load(...).profiles
                    │ — update(mutate): state = mutate(state); persist as
                    │   ProfilesData(profiles: next) via the store
                    │
                    └── activeProfileProvider = Provider<Profile?>(
                          (ref) => activeProfileOf(ref.watch(profilesProvider)),
                        )
```

`activeProfileOf(List<Profile>)` is a plain function living in
`packages/ebc_db` (not inlined as `.firstOrNull` at the call site) — the
"index 0 is active" convention is a fact about `ProfilesData`'s shape, so
it belongs next to the type that owns it, same reasoning as `uuid`
regeneration below. `activeProfileProvider` becomes a one-line wrapper
around it rather than re-deriving the convention itself; anything else in
`lib/` that needs "the active profile" calls the same function instead of
independently reaching for `.firstOrNull`.

- **"Global broadcast, subscriber picks what it needs"** is still exactly
  what Riverpod's `select()` gives you — `GeneratedMessage`/`PbList` both
  implement deep, recursive `==` (verified against the `protobuf` package
  source), so a selector watching `settingsProvider.select((s) =>
  s.unitSettings)` or the whole `profilesProvider` list reliably detects
  any change on its path, with no manual "which stream covers this"
  bookkeeping.
- **Atomicity** lives in each notifier's `update()`: `state` is only ever
  assigned once, fully computed — there is no observable half-mutated
  state, no transaction needed for in-memory consistency. This replaces
  every `store.runInTransaction(TxMode.write, () { ... })` block in
  `app_state_provider.dart` today.
- **"Select a different profile"** = `ref.read(profilesProvider.notifier)
  .update((profiles) => setActiveProfileOf(profiles, uuid))` — the
  reorder-to-index-0 mechanic itself lives in `packages/ebc_db` as
  `setActiveProfileOf(List<Profile>, String uuid) -> List<Profile>`,
  paired by name with `activeProfileOf` above: one reads the convention,
  the other writes it, neither re-implemented at the call site. Same
  mechanic Doc #3-era ObjectBox code
  and the original `Db.profiles` sketch both used, just no longer inlined
  in app code. See Open Questions for the still-unresolved interaction
  with manual display-order reordering, if that's ever added.

### Phase 5 — Legacy data migration (via `ob-dump`)

**UX flow — decided.** Migration is not a silent background step and not
tied to whether `settings.ebcp`/`profiles.ebcp` already exist as the only
signal — it's a **gate screen shown before Home, driven by whether a
legacy ObjectBox store is present on disk.** ObjectBox lived at
`<applicationSupportDirectory>/data.mdb` (+ `lock.mdb`) — see `main.dart`
on `main` (`_openStore`'s `File('$directory/data.mdb').exists()` check) —
same directory `profiles.ebcp`/`settings.ebcp` now live in.

- [ ] **Detect before Home, not during normal boot.** At startup, after
      opening (or seeding) `profiles.ebcp`/`settings.ebcp` as today, check
      for `data.mdb` in `applicationSupportDirectory`. If present, route to
      a new gate screen instead of `Home` — same idea as `_DbResetBanner`
      being decided before `runApp`, just a full screen instead of a
      banner, since it can block navigation rather than merely inform.
- [ ] **Ask, don't migrate automatically.** The gate screen's first state
      is a dialog/prompt: "Found an old database — import its data?" (copy
      TBD, needs l10n keys in both `.arb` files). Two choices — confirm
      (proceed to migrate) or decline. Declining's exact consequence (skip
      to Home this launch and ask again next launch? skip permanently
      until the old dir is manually removed?) is not decided yet — flag as
      an open question below, don't guess an answer while implementing.
- [ ] **On confirm, run `LegacyMigrator` with a progress UI**, not a
      silent await: a spinner + "Migrating…" label at minimum; a
      determinate progress bar is nicer-to-have if `LegacyMigrator` can
      report incremental progress (e.g. "profile N of M") without
      restructuring the one-shot decode — if it can't cheaply, ship the
      indeterminate spinner first, revisit later.
- [ ] `LegacyMigrator` itself (the decode step this screen drives): use
      the `ob_dump_reader` Dart package (no FFI, no `objectbox-c`
      dependency) to decode `data.mdb` straight from Dart, driven by the
      app's shipped `objectbox-model.json`. Decode the old relational graph
      (`Owner.activeProfile`, `Profile.weapon/.ammo/.sight` `ToOne` ids),
      **copy** each profile's linked Weapon/Ammo/Sight into one `Profile`
      message, collect them into `profiles.ebcp`'s list with the old
      active profile placed at index 0. Write one `SettingsData` (all six
      settings sub-messages ported) into `settings.ebcp`.
- [ ] **On completion, proceed to Home** — the gate screen is a one-shot
      detour on the boot path, not a persistent route; it never appears
      again once there's nothing left to detect (see below).
- [ ] **Dev-stage: never delete the old `data.mdb`/`lock.mdb` from disk**,
      migration confirmed or not. (Longer-term — once this ships and is
      trusted — the old plan of renaming the directory as a fallback for
      one release cycle, see Open Questions, is still the eventual target;
      just not while this is still being built and tested.) This also
      means the detection check (`data.mdb` exists) alone can't be what
      prevents re-prompting after a successful migration during
      development — needs its own guard (e.g. a marker written once
      migration completes, checked alongside/instead of raw file
      existence) so confirming once doesn't re-show the gate on every
      subsequent launch just because the old file is still sitting there.

## Verification

1. Fresh install (no `settings.ebcp`, no `profiles.ebcp`, no legacy
   ObjectBox dir) → seeds default `SettingsData` and a seeded
   `profiles.ebcp`.
2. Create a profile (weapon/ammo/sight picked from collection or built via
   wizard) → `profiles.ebcp` rewritten with the new profile appended;
   `settings.ebcp` untouched. Replace weapon/ammo/sight on an existing
   profile → only that entry in the list changes before the file is
   rewritten.
3. Select a different profile → `profiles.ebcp` rewritten with that
   profile moved to index 0; restart app → same selection persists.
4. Kill the process mid-write to `profiles.ebcp` (e.g. `SIGKILL` right
   after a save) → next launch recovers from `profiles.ebcp.bak`, never a
   torn file; `settings.ebcp` is completely unaffected by a crash during a
   `profiles.ebcp` write, and vice versa.
5. Fresh install with a **legacy** ObjectBox dir present, no `settings.ebcp`/
   `profiles.ebcp` yet → `LegacyMigrator` runs once, produces an equivalent
   `profiles.ebcp` (old active profile at index 0) + `settings.ebcp`, old
   dir preserved (renamed) rather than deleted.
6. Decoded `settings.ebcp` validates against `settings.schema.json`;
   decoded `profiles.ebcp` validates against `profiles.schema.json`.
7. (Phase 3.5, not yet wired to any UI) An `EbcpData` built from one
   profile round-trips through `EbcpFile.encode`/`decode` and validates
   against `ebcp.schema.json` with `settings_data` absent; one built with
   several profiles + settings round-trips and validates with
   `settings_data` present. Both already covered by
   `test/ebcp_test.dart` at the package level — this item is about the
   eventual app-level share/import flow, once built.

## Phase 3.5 Sketch — `.ebcp` Export/Import UX

**Status update — `.a7p` is done, out of order; `.ebcp` is still not
started.** `a7p_service.dart`/`a7p_converter.dart` were ported to target
`ebc_db.Profile`/`Weapon`/`Ammo`/`Sight`/`Zero` directly, and
`my_profiles_screen.dart` now wires: whole-profile `.a7p` export (range
picker, same 5 ranges as before), whole-profile `.a7p` import (new profile,
via `AppStateNotifier.importProfile` — mints a fresh `uuid` via
`copyWithFreshUuid`, per the invariant below), and per-component `.a7p`
import inside the "replace ammo"/"replace sight" action sheets (imports a
whole `.a7p` profile, takes just its `ammo`/`sight`). Fields a7p has no
concept of (look angle, altitude, latitude, azimuth, coriolis, barrel
length, calibrated magnification, zero elevation) are left unset on
import rather than defaulted to a sentinel value — `sanitizeProfile`
still clamps whatever *is* set. `.ebcp` (both entry points below) remains
exactly as originally sketched in this section: not implemented, not
scheduled, no code.

Not implemented, not scheduled, no code — captured here so Phase 3.5
doesn't have to rediscover this from scratch. `.ebcp` becomes the one
format for both single-profile sharing and whole-app backup; the
difference between the two is entirely which `EbcpData` fields a given
file happens to populate, not a separate file kind.

Two entry points, each with its own export *and* import behavior — not a
single global export flow and a single global import flow. What a given
action does is determined by which screen it's on, not by inspecting file
content first (content only ever narrows what's *possible*, e.g. "this
file has no profiles," never what's *offered*).

**Entry point: Profiles screen (open / export / share a single profile)**
- **Export** always exports exactly the one profile currently in view —
  no picker, no checkboxes: `EbcpData{ profiles_data: [ProfilesData{
  profiles: [thatOneProfile] }] }`, `settings_data` unset.
- **Import**: opening a file here only ever imports a profile. If the
  file's `profiles_data` is non-empty, the user picks **one** profile from
  it to bring in. If the file has no profile data at all (e.g. it's a
  settings-only backup), there's nothing this entry point can do with it.
  Settings are never touched from this screen, regardless of what the
  file otherwise contains.

**Entry point: Settings screen / Backup**
- **Export** always exports everything — all local profiles plus
  settings, unconditionally: `EbcpData{ profiles_data: [ProfilesData{
  profiles: <all local profiles> }], settings_data: <local Settings> }`.
  No checkboxes on export from this screen; that choice only exists on
  import.
- **Import** offers a three-way choice — **all profiles** (if the file
  has any), **settings only**, or **everything** — but no individual
  profile picking at this entry point: bringing in profiles here is
  all-or-nothing, unlike the Profiles-screen single-pick flow above.

**`uuid` lifecycle — resolved.** One invariant, not a grab-bag of
per-action rules: **a `Profile` keeps its `uuid` when referenced, gets a
fresh one whenever it's copied.**

1. **Reorder never touches `uuid`.** Moving a profile to index 0 (select
   active) or anywhere else in the list is the same `Profile`, just at a
   different position — nothing is copied, so nothing regenerates.
2. **Creating a new profile mints a `uuid`.** Nothing to copy from, so
   this is just "assign one" rather than "regenerate one."
3. **A profile entering local `ProfilesData` from outside (import) always
   gets a fresh `uuid`,** never reusing whatever value the source file
   carried — not a case-by-case "does this collide?" check, the incoming
   value is simply never trusted.
4. **Export is the same operation, in reverse.** Building an `EbcpData`
   from local profiles is *also* "copying a `Profile` from one message
   into another" (`ProfilesData` → `EbcpData`), so rule 3 applies
   symmetrically: export regenerates `uuid` too, through the same
   mechanism, not a separately-implemented one.

This is the same invariant Doc #8.3's `duplicateProfile` already relies on
(a within-`ProfilesData` copy also gets a fresh `uuid`, for the same
reason two profiles can't share one) — three call sites, one rule.
**Implementation implication:** this argues for one `copyWithFreshUuid
(Profile) -> Profile`-shaped helper living in `packages/ebc_db` itself
(not app-level `lib/` code) that `duplicateProfile`, export, and import
all go through, rather than each site regenerating a `uuid`
independently — the invariant should hold *by construction*, not by
every caller remembering to do the right thing.

**API convention: every creation/copy helper returns the new value,
none mutate in place.** `copyWithFreshUuid`, and anything else in
`packages/ebc_db` that creates or copies a `Profile`/`ProfilesData`/
`EbcpData` (a future "new profile" helper included), follows the same
shape as `MsgStore.update()`'s `mutate` callbacks already do elsewhere in
this doc: take the old value, return a new one, never reach in and modify
the argument. Consistent with protobuf messages being treated as
copy-on-write throughout this design (see "Global broadcast, subscriber
picks what it needs" above) rather than mutated shared state.

**Standalone ammo/sight — resolved: they don't exist.** There is no such
thing as user-owned ammo or sight data outside a `Profile` — that was the
whole point of the 1:1:1:1 simplification (see Core Design). `EbcpData`
correctly has no field for them because there's nothing to put there. The
only ammo/sight data *not* embedded in a profile is the built-in
collection (bundled JSON reference data — calibers, bullets, sights —
shipped with the app, not user data), which is a completely different
concern from `.ebcp` backup/share and out of scope here; there's a
separate idea for that case, deferred indefinitely, not sketched.

## Open Questions

- **Legacy migration gate — decline behavior and re-prompt guard not
  decided (Phase 5).** If the user declines the "found an old database,
  import it?" prompt, does the gate ask again next launch, or stay
  silent until the old directory is manually removed? Separately, since
  dev builds keep `data.mdb` on disk even after a successful migration
  (see Phase 5), raw file existence can't remain the sole trigger forever
  — some completed-migration marker is needed so a successful run doesn't
  re-show the gate on every subsequent launch. Needs a decision before
  Phase 5 ships, not just while it's being developed.
- **No exclusive write lock on `settings.ebcp`/`profiles.ebcp` — not
  designed yet.** Confirmed: `MsgStore` (`packages/ebc_db/lib/src/
  msg_store.dart`) has no file-locking of any kind — nothing stops two
  processes (or two windows of the same process) from both opening,
  mutating, and independently tmp-write+rename+`.bak`-rotating the same
  file, with whichever save lands last silently winning and the other's
  changes vanishing. Only one client may ever hold write access at a time,
  by design — this needs to be enforced, not merely assumed. On desktop
  specifically: launching the app a second time (e.g. double-clicking the
  icon again, or a second `open`/protocol-handler invocation while it's
  already running) must **focus the existing window**, not open a second
  one — there is deliberately no scenario where two windows of this app
  run concurrently against the same data directory. No design done yet for
  either half (an actual file lock — e.g. an OS advisory lock via `dart:io`
  `File.lock()`/`RandomAccessFile.lock()` held for the process's lifetime,
  checked at startup — or the desktop single-instance/focus-existing-window
  mechanism, which is a windowing/platform-channel concern, not a
  `packages/ebc_db` one). Needs its own pass before shipping the desktop
  target.
- ~~**Do entities need any id at all?**~~ — resolved: yes, a client-generated
  `uuid`, but only on `Profile` — `Ammo`/`Sight` lost theirs once
  they stopped being list elements.
- **Reordering vs. "index 0 = active" conflict — still open.** An explicit
  `Settings.active_profile_uuid` pointer was drafted specifically to
  resolve this and was rejected in favor of staying list-position-based.
  So: if the Profiles screen ever wants manual display-order reordering
  independent of "which one is active," that still needs a UI convention
  (e.g. active profile always pinned to index 0, manual reordering only
  applies to `profiles[1:]`) — needs a decision before Phase 4 UI wiring,
  same as it would have under the original single-`Db` design.
- ~~**`.ebcp` sharing/backup message shape and export/import UX**~~ —
  resolved/sketched: `EbcpData`'s shape, and per-entry-point
  export/import behavior (Profiles screen: export always the one profile
  in view, import a single picked profile; Settings/Backup screen: export
  always everything unconditionally, import a three-way all-profiles/
  settings-only/everything choice — see "Phase 3.5 Sketch" above),
  the `uuid` lifecycle invariant (fresh `uuid` on every copy — reorder
  excepted, import/export/`duplicateProfile` all count as copies), and
  standalone ammo/sight (they don't exist in this schema — see "Phase 3.5
  Sketch" above) are all resolved. **Still open, deferred to Phase 3.5,
  not this doc:** today's `.ebcp`
  (`packages/ebalistyka_db/lib/src/export/ebcp_file.dart`, a ZIP archive
  containing one JSON file) is completely untouched — nothing yet
  produces or reads an `EbcpData` file from the running app.
- ~~**Package layout**~~ — resolved (Phase 0): new `packages/ebc_db`
  package; `ebalistyka_db` retired in Phase 6 once migration ships.
- ~~**Debounce vs. immediate persistence**~~ — resolved (Phase 2):
  `MsgStore<T>(file, encode:, decode:, debounce: ...)` is configurable,
  defaulting to `Duration.zero` (immediate); `flush()` forces a pending
  write through on app pause/dispose. `settingsProvider`/`profilesProvider`
  each own an independent `MsgStore` instance, so debounce windows don't
  interact across the two files.
- **Schema versioning:** `schema_version` lives on both `ProfilesData` and
  `SettingsData` independently — the actual migration strategy between
  future schema versions is still undefined, out of scope for this doc but
  should be decided before shipping v1 of the new format.
- ~~**Field validation belongs in `ebc_db`, not scattered across `lib/`**~~
  — resolved (design; first slice built — `profiles.schema.json`'s 18
  roles' bounds are now generated and wired into `FC`, see Phase 7 — but
  `settings.schema.json`/convertors and the actual centralized clamp/reject
  hook are still pending). Today, every guard against
  an invalid stored value (unset-vs-zero via `hasX()`, range clamping via
  `FieldConstraints`, the `bcG1`/`bcG7` null-vs-zero conflation fix, etc.)
  lives ad hoc in `lib/core/extensions/*` getters/setters and each
  provider's individual `updateX` method — see `8.3impl.md`'s
  "Post-migration bug fixes" section for the concrete instances found.
  **Decision:** flip today's direction. Right now `lib/core/models/
  field_constraints.dart` (`FC`) is the hand-maintained source and
  `schema/*.schema.json`'s numeric bounds are a manually ported,
  manually unit-converted copy (see e.g. `look_angle_rad`'s
  `-1.5707963267948966` alongside a `"FC.lookAngle, degree→radian"`
  comment) — synced by a human, which is the actual bug class this item
  was opened for. Instead, the numeric-bounds half of `FC` (`minRaw`/
  `maxRaw`/`clamp()`) gets **generated at build time from the schema
  files** into `packages/ebc_db`, carrying no unit concept at all (not
  even an internal enum) — just numeric bounds keyed by role name.
  `FC` itself becomes a thin app-layer wrapper that pairs each generated
  bound by hand with the `dart_bclibc.Unit` it's actually expressed in,
  plus the UI-only `stepRaw`/`accuracy` fields, which have no
  schema representation and stay hand-authored. Not every `FC` role maps
  to a schema field (display-only trajectory output and one
  never-fully-specified convertor bound don't persist anywhere) — those
  stay hand-authored `const`s in `ebc_db` too, just not generated. See
  Phase 7 for the concrete mechanism and the open sub-decisions
  (raw-unit semantics per field, the role-name↔JSON-Pointer mapping).

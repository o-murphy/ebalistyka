# Protobuf Storage Migration — Replace ObjectBox with an Embedded Protobuf Document

> **Doc #8 — Status: DRAFT (proposed, not started)**
> Supersedes Doc #3 (`3.OBJECTBOX_MIGRATION.md`) as the storage layer. Doc #3
> stays as historical record of why/how ObjectBox was adopted; this doc
> replaces it as the *current* target architecture.

> No multi-user / remote-sync support is planned (see Owner-entity removal
> discussion). The new schema has no `Owner`, no relational ids, and no
> `ToOne`/`ToMany` — it is a single nested document, modeled after
> [`a7p`](https://github.com/o-murphy/a7p)'s `dart/` package (protobuf +
> JSON Schema, MD5-hash-prefixed file format).

---

## Context

The app currently persists through ObjectBox (`packages/ebalistyka_db`):
a relational-ish object graph (`Weapon`/`Ammo`/`Sight`/`Profile`/settings
entities) linked via `ToOne<Owner>`/`ToMany` backlinks, queried per-owner,
watched via per-box `Query.watch()` streams (see Doc #3, Doc #4).

Two problems with keeping that shape long-term:

1. **`Owner` is dead weight.** It exists solely to prep for multi-user /
   remote sync, which is not going to be built. Every entity carries an
   unused `ToOne<Owner>` and every query filters by it.
2. **ObjectBox itself is being replaced.** `objectbox-c` is a closed-source
   binary; the project's own [`ob-dump`](https://github.com/o-murphy/ob-dump)
   tool exists specifically to read data back out of an ObjectBox store
   without depending on that binary, precisely so this kind of migration is
   possible later without hostage data.

Rather than doing ObjectBox schema surgery now (drop `Owner`, regenerate
codegen, retire model UIDs) and then throwing that work away when the
storage engine changes, this doc defines the target architecture directly
and treats `Owner` removal as a side effect of the rewrite, not a separate
step.

## Core Design

- **The whole app is one message.** `Db` is the root protobuf message and,
  in memory, *is* the global app state — not a cache of it. There is no
  separate `AppState` class to keep in sync with a database; the notifier
  holding `Db` **is** the source of truth.
- **File persistence is just a durability layer.** Writing `Db` to disk is
  serialization for the next cold start, not the primary read/write path —
  the same relationship `.a7p` has to a single ballistic profile, just
  scoped to the whole app instead of one profile.
- **No cross-references.** No `ToOne`/`ToMany`, no relational ids. Entities
  that must appear in more than one place (e.g. reusing an ammo config
  across profiles) are **copied**, not shared. This trades storage
  duplication for the elimination of an entire class of bugs (dangling
  refs, orphaned rows, cascade-delete logic) — acceptable because the
  dataset is small (single device, no sync).
- **List order encodes "active".** There is no separate `activeProfileId`/
  `activeIndex` field anywhere. The first element of a `repeated` list is
  the active one:
  - `Db.profiles[0]` — the active profile (shown on Home).
  - `Profile.ammo[0]` — the active ammo for that profile.
  - `Profile.sights[0]` — the active sight for that profile.
  Selecting a different item means **reordering the list** (move the
  selected item to index 0), not writing an id pointer elsewhere. This is
  simpler than `Owner.activeProfile` but changes how "select X" is
  implemented everywhere (see Open Questions — reordering UX).
- **`Weapon` becomes a value, not a shared row.** Today `Weapon` is its own
  ObjectBox box referenced by `Profile.weapon` (`ToOne`). In the new schema
  each `Profile` embeds exactly one `Weapon` message directly — a profile
  and its rifle are one document, matching how the UI already treats them
  (a profile *is* "rifle + sight + ammo set").

## Message Schema (sketch)

Illustrative only — the actual schema lives at
`packages/ebc_db/proto/ebc_db.proto` (Phase 1, done) and is the source of
truth; don't hand-sync every field here. Two structural refinements made
while writing it, not reflected in the sketch below: `Ammo` nests its
`zero_*` fields into a `Zero` sub-message (same idea as embedding settings
into `Db` — group by sub-concern instead of one flat bag), and
`ConvertorsState` (27 flat fields covering 8 unrelated sub-converters) is
split the same way, reusing a generic `UnitValue{value, last_unit}` message
for the five simple value+unit pairs (length/weight/pressure/temperature/
torque) and dedicated messages for the composite ones (`AnglesConv`,
`VelocityConv`, `DistanceConvTargetSize`).

```proto
syntax = "proto3";
package ebalistyka;

message Db {
  uint32 schema_version = 1;

  GeneralSettings general_settings = 2;
  UnitSettings unit_settings = 3;
  TablesSettings tables_settings = 4;
  ReticleSettings reticle_settings = 5;
  ConvertorsState convertors_state = 6;
  ShootingConditions shooting_conditions = 7;

  repeated Profile profiles = 8; // profiles[0] = active profile
}

message Profile {
  string ui_key = 1;   // client-generated UUID, addressing only — no
                        // relational meaning (see Open Questions, resolved)
  string name = 2;
  Weapon weapon = 3;          // embedded, not a reference
  repeated Ammo ammo = 4;     // ammo[0] = active
  repeated Sight sights = 5;  // sights[0] = active
}

message Weapon   { /* same fields as today's ebalistyka_db.Weapon, minus id/owner — no ui_key, not independently addressed */ }
message Ammo     { string ui_key = 1; /* + same fields as today's ebalistyka_db.Ammo, minus id/owner */ }
message Sight    { string ui_key = 1; /* + same fields as today's ebalistyka_db.Sight, minus id/owner */ }

message GeneralSettings     { /* minus id/owner */ }
message UnitSettings        { /* minus id/owner */ }
message TablesSettings      { /* minus id/owner */ }
message ReticleSettings     { /* minus id/owner */ }
message ConvertorsState     { /* minus id/owner */ }
message ShootingConditions  { /* minus id/owner */ }
```

A parallel `schema/ebc_db.schema.json` (JSON Schema) validates the
decoded-to-JSON shape of `Db`, mirroring `a7p`'s dual-artifact pattern —
gives a human-readable/debuggable validation path independent of whatever
the protobuf compiler produced, and a way to sanity-check a loaded file
before trusting it into the app state.

## Runtime Architecture — Replacing ObjectBox's `Query.watch()`

ObjectBox's per-box `watch()` streams don't map onto a single-document
store. Replacement:

```
dbFileProvider   (Provider<File> — path to db.pb)
    │
    └── dbProvider (Notifier<Db>)
            │  — in-memory Db IS the app state
            │  — build(): load + validate db.pb on cold start (or seed)
            │  — every mutation goes through one method:
            │
            │      Db _update(Db Function(Db current) mutate) {
            │        final next = mutate(state);
            │        state = next;              // Riverpod notifies watchers
            │        unawaited(_persist(next));  // async, atomic file write
            │        return next;
            │      }
            │
            ├── activeProfileProvider   = dbProvider.select((db) => db.profiles.firstOrNull)
            ├── profilesProvider        = dbProvider.select((db) => db.profiles)
            ├── generalSettingsProvider = dbProvider.select((db) => db.generalSettings)
            ├── unitSettingsProvider    = dbProvider.select((db) => db.unitSettings)
            └── ... one selector per top-level field, same pattern as today's
                "synchronous access" providers in settings_provider.dart
```

- **"Global broadcast, subscriber picks what it needs"** is exactly what
  Riverpod's `select()` already gives you — no custom stream/broadcast
  plumbing needed, just stop hand-rolling per-box `Query.watch()`
  subscriptions and let `ref.watch(xProvider.select(...))` do the diffing.
- **Atomicity** lives entirely in `_update()`: `state` is only ever
  assigned once, fully computed — there is no observable half-mutated
  state, no `runInTransaction()` needed for in-memory consistency. This
  replaces every `store.runInTransaction(TxMode.write, () { ... })` block
  in `app_state_provider.dart` today.
- **File-write atomicity** (surviving a crash mid-save) is a separate,
  narrower problem: write the new bytes to `db.pb.tmp`, flush, then rename
  over `db.pb` (atomic on all target platforms' filesystems). Keep one
  rotated backup (`db.pb.bak`) for one write cycle as a belt-and-suspenders
  recovery path.

## Implementation Steps

### Phase 0 — Confirm scope
- [x] Package layout decided: new package **`packages/ebc_db`**. It replaces
      `ebalistyka_db` as the storage layer; `ebalistyka_db` is retired once
      migration ships (see Phase 6, Open Questions).
- [x] `ui_key` decision made (see Open Questions) — `Profile`/`Ammo`/`Sight`
      each get a client-generated `string ui_key` field for UI/route
      addressing only.
- [x] `.proto` field list finalized — `packages/ebc_db/proto/ebc_db.proto`
      (1:1 port of current ObjectBox entity fields, minus `id`/`owner`, plus
      `ui_key` where noted; `Ammo.zero_*` and `ConvertorsState`'s 27 flat
      fields further split into sub-messages, see Message Schema section).

### Phase 1 — Schema artifacts — DONE
- [x] Write `packages/ebc_db/proto/ebc_db.proto` (all messages above).
- [x] Write `packages/ebc_db/schema/ebc_db.schema.json` (JSON Schema counterpart).
- [x] Port `a7p`'s codegen scripts into `packages/ebc_db`:
  - `bin/generate_proto.dart` equivalent (`protoc` + `protoc_plugin` → Dart classes).
  - schema-embedding step (`lib/src/generated/ebc_db_schema.g.dart`,
    same pattern as `a7p_schema.g.dart`).

### Phase 2 — Persistence layer — DONE
- [x] `DbFile` in `packages/ebc_db` (analogous to `a7p_file.dart`):
      MD5-hash-prefixed protobuf-bytes encode/decode, matching `.a7p`'s wire format.
- [x] Atomic write helper (`tmp` + flush + rename, `.bak` rotation) — `DbStore`.
- [x] Cold-start load: read `db.pb`, hash-check, JSON-Schema-validate the
      decoded shape, fall back to seed data if missing/corrupt (mirrors
      today's `dbWasResetProvider` behavior in `db_provider.dart`) — `DbStore.load()`.

### Phase 3 — Riverpod integration
- [ ] `dbProvider` (`Notifier<Db>`) + `_update()` per above.
- [ ] One `select()`-based provider per top-level `Db` field, replacing
      today's `settingsProvider`/`unitSettingsProvider`/
      `tablesSettingsProvider`/`reticleSettingsProvider`/
      `convertorStateProvider`/`shotConditionsProvider`/`appStateProvider`.
- [ ] Rewrite every notifier method currently doing
      `_store.box<X>().put(...)` as a `dbProvider.notifier._update((db) => ...)`
      call building a new `Db` via `rebuild()`/copy-with.

### Phase 4 — "Active item" semantics
- [ ] Implement "select = move to index 0" for profiles, ammo, sights.
- [ ] Resolve list-reordering UX vs. "index 0 = active" conflict (see Open
      Questions) before wiring the Profiles/Ammo/Sight screens to it.

### Phase 5 — Legacy data migration (via `ob-dump`)
- [ ] Use the `ob_dump_reader` Dart package (no FFI, no `objectbox-c`
      dependency) to decode the existing `data.mdb` straight from Dart,
      driven by the app's shipped `objectbox-model.json`.
- [ ] One-time `LegacyMigrator`: on first launch of the new build, if
      `db.pb` doesn't exist yet but an ObjectBox directory does — decode the
      old relational graph (`Owner.activeProfile`, `Profile.weapon/.ammo/.sight`
      `ToOne` ids) and **copy** each profile's linked Weapon/Ammo/Sight into
      that profile's embedded `Db` message (this is the one place the
      "duplicate via copy" rule gets exercised against real data instead of
      designed in the abstract).
- [ ] Write the resulting `Db` out via Phase 2's persistence layer.
- [ ] Keep the old ObjectBox directory as a fallback for one release cycle
      (rename, don't delete, until the migration has shipped and been
      validated).

### Phase 6 — Cleanup
- [ ] Remove `packages/ebalistyka_db` entirely (dependency, package
      reference in root `pubspec.yaml`/melos config, ObjectBox entities,
      generated code, its `debug_test.dart`) once migration is validated —
      superseded by `packages/ebc_db`.
- [ ] Update Doc #3 and `MasterProject.md` §6.3/§6.5 to point at this doc.

## Verification

1. Fresh install (no `db.pb`, no legacy ObjectBox dir) → seeds default `Db`.
2. Create/edit/delete profile, ammo, sight → in-memory state updates via
   `_update()`, UI reflects it through selectors.
3. Select a different profile/ammo/sight → target moves to index 0,
   restart app → same selection persists.
4. Kill the process mid-write (e.g. `SIGKILL` right after a save) → next
   launch recovers cleanly from `db.pb.bak` or the last successful
   `db.pb`, never a torn file.
5. Fresh install with a **legacy** ObjectBox dir present, no `db.pb` yet →
   `LegacyMigrator` runs once, produces an equivalent `Db`, old dir
   preserved (renamed) rather than deleted.
6. Decoded `Db` (post-migration and post-normal-use) validates against
   `ebalistyka.schema.json`.

## Open Questions

- ~~**Do entities need any id at all?**~~ — resolved: yes, a client-generated
  `ui_key` (UUID) on `Profile`/`Ammo`/`Sight`, generated once on creation,
  used only for widget keys/route params — never for storage relationships
  (no relational meaning, just addressing).
- **Reordering vs. "index 0 = active" conflict:** if a user manually
  reorders their profile list for display purposes (not selection), does
  that clash with "profiles[0] is active"? Might need a UI convention
  (e.g. active profile always pinned to top, manual reordering only
  applies to profiles[1:]) — needs a decision before Phase 4.
- ~~**Package layout**~~ — resolved (Phase 0): new `packages/ebc_db`
  package; `ebalistyka_db` retired in Phase 6 once migration ships. Open
  sub-question: how long the two packages coexist during migration
  (both present so `LegacyMigrator` can still read the old store).
- **Debounce vs. immediate persistence:** should `_update()` write to disk
  on every call, or debounce rapid-fire updates (e.g. dragging a slider)?
  Affects Phase 2/3 design of `_persist()`.
- **Schema versioning:** `schema_version` field is in the sketch but the
  actual migration strategy between future versions (once this ships) is
  undefined — out of scope for this doc but should be decided before
  shipping v1 of the new format, not after.

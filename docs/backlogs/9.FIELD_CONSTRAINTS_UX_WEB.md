### Phase 7 — Field constraint unification (resolves the "Field validation
belongs in ebc_db" open question in Doc #8's Open Questions)

**Scope for this pass: `profiles.schema.json` only** (`Weapon`/`Sight`/
`Zero`/`Ammo`). `settings.schema.json` (`GeneralSettings`/`TablesSettings`/
`ShootingConditions`/`ReticleSettings`/`ConvertorsState`) is deferred to a
later pass — convertors especially, since three of its fields have
unresolved unit/range discrepancies (see below) that need a product
decision, not just mechanical generation. Roles covered this pass, all
sourced from `profiles.schema.json`:
`projectileDiameter` (`Weapon.caliber_inch`/`Ammo.caliber_inch`), `twist`
(`Weapon.twist_inch`), `barrelLength` (`Weapon.barrel_length_inch`),
`sightHeight` (`Sight.sight_height_inch`/`.sight_horizontal_offset_inch`),
`magnification` (`Sight.min_magnification`/`.max_magnification`/
`.calibrated_magnification`), `zeroDistance` (`Zero.distance_meter`),
`lookAngle` (`Zero.look_angle_rad`), `altitude` (`Zero.altitude_meter`),
`temperature` (`Zero.temperature_c`/`.powder_temperature_c`/
`Ammo.muzzle_velocity_temperature_c`), `pressure` (`Zero.pressure_h_pa`),
`humidity` (`Zero.humidity_frac`), `latitude` (`Zero.latitude_deg`),
`azimuth` (`Zero.azimuth_deg`), `projectileWeight` (`Ammo.weight_grain`),
`projectileLength` (`Ammo.length_inch`), `ballisticCoefficient`
(`Ammo.bc_g1`/`.bc_g7`), `muzzleVelocity` (`Ammo.muzzle_velocity_mps`),
`powderSensitivity` (`Ammo.powder_sensitivity_frac`) — 18 roles, all with
clean, unambiguous schema bounds (no x-discrepancy notes, unlike several
`ConvertorsState` fields). Some of these roles (`temperature`, `pressure`,
`humidity`, `altitude`, `latitude`, `azimuth`, `lookAngle`) are *also* used
by `settings.schema.json`'s `ShootingConditions` with identical bounds —
generating them from `profiles.schema.json` now doesn't block wiring
`ShootingConditions` to the same generated constants later, since the
numbers agree.

- [x] Extend `packages/ebc_db/bin/embed_schema.dart` to also emit
      `packages/ebc_db/lib/src/generated/field_constraints.g.dart`: one
      `const FieldBounds` per persisted numeric field (`minRaw`/`maxRaw`/
      `clamp()`), generated at build time from `schema/profiles.schema.json`
      the same offline way `kSettingsSchemaJson`/`kProfilesSchemaJson`/
      `kEbcpSchemaJson` already are — no runtime `json_schema` parsing.
      `_fieldConstraintRoles` (role → `($defName, propertyName)` list) lives
      in the generator; it fails loudly (`exit(1)`) on an unmapped numeric
      field, a stale/typo'd mapping entry, or disagreeing bounds across a
      role's mapped paths.
- [x] No unit concept in `ebc_db` at all — not even an internal enum.
      `ebc_db.FieldBounds` (`packages/ebc_db/lib/src/field_bounds.dart`)
      carries only `minRaw`/`maxRaw`/`clamp()`. Named `FieldBounds`, not
      `FieldConstraints` — the app already has its own `FieldConstraints`
      class (`lib/core/models/field_constraints.dart`) and re-using the name
      in `ebc_db`'s exports collided (`ambiguous_import`) at every call site
      that imports both packages unqualified (convertor VMs, etc.).
      Since the type carries no unit, **the generated role names carry the
      wire unit as a suffix instead** (`temperatureC`, `altitudeMeter`,
      `lookAngleRad`, `sightHeightInch`, `twistInch`, etc. — see
      `FieldLimits` in the generated file), mirroring the schema's own
      field-naming convention (`temperature_c`, `look_angle_rad`). Only the
      two dimensionless roles (`magnification`, `ballisticCoefficient`) stay
      bare, matching their wire fields (`min_magnification`, `bc_g1`), which
      also carry no unit suffix.
- [x] Role-name ↔ JSON Pointer mapping table lives once, inside the
      generator script (`_fieldConstraintRoles` in
      `packages/ebc_db/bin/embed_schema.dart`) — fails loudly on an
      unmapped numeric field, as above.
- [x] Field-by-field audit of wire unit vs. today's `FC.x.rawUnit`, across
      all 18 profile roles. Confirmed mismatches requiring an explicit
      conversion in the app-layer wrapper (next item): `lookAngleRad`
      (radians in `ebc_db` vs. `Unit.degree` picker — `* 180 / pi`),
      `sightHeightInch`/`projectileLengthInch`/`projectileDiameterInch`
      (inch in `ebc_db` vs. `Unit.millimeter` picker — converted via
      `dart_bclibc`'s existing `double.convert(Unit, Unit)` extension, not a
      hand-rolled `* 25.4`/`* 180 / pi`, matching how every other unit
      conversion in this codebase is done), and
      `twistInch` (signed -30..30 in `ebc_db`, storage's actual encoding,
      vs. the picker's magnitude-only 0..30 paired with a separate direction
      toggle in `weapon_wizard_notifier.dart` — `FC.twist.minRaw` stays a
      hardcoded `0.0` floor, only `maxRaw` resolves from the generated
      bound). The other 13 roles use an identical unit in both places, so
      no conversion is needed for those.
- [x] Rewrite `lib/core/models/field_constraints.dart` (`FC`): all 18
      profile-scoped roles now resolve `minRaw`/`maxRaw` from
      `ebc_db.FieldLimits` (with the conversions above where needed) instead
      of a hand-copied literal; `rawUnit`/`stepRaw`/`accuracy` stay
      hand-authored, as planned (no schema representation). These entries
      changed from `static const` to `static final` — reading an instance
      field (`FieldLimits.x.minRaw`) off a const object isn't legal inside
      another `const` expression in Dart, and nothing in the app requires
      `FC.x` to be compile-time const (verified: no `const Widget(...FC.x...)`
      or `case FC.x` usage anywhere in `lib/`). Runtime-verified the
      resolved values match the old hardcoded ones; `projectileDiameter`'s
      converted maxRaw lands ~1e-15 off the old clean `30.0` due to inch↔mm
      float conversion — functionally inert (well under the field's own
      `accuracy: 2`). Non-profile roles
      (`windSpeed`, `windDirection`, `targetDistance`, `drop`, `windage`,
      `adjustment`, `velocity`, `energy`, `tableRange`, `distanceStep`, all
      `convertor*`, `torque`, `targetSize`) are untouched — out of scope,
      see below.
- [x] `schema/profiles.schema.json` itself no longer hand-duplicates bounds
      across fields that share one constraint — added `$defs/TemperatureC`,
      `CaliberInch`, `SightHeightInch`, `BallisticCoefficient`,
      `MagnificationBounds`, `$ref`'d (or `allOf`-composed, where per-field
      `type`/`default` still differ, e.g. `calibrated_magnification` being
      nullable) from every field that used to repeat the same

      `bc_g1`/`bc_g7`; the three magnification fields). `description` stays
      on each field itself (sibling of `$ref`/`allOf`), not moved into the
      shared `$defs` entry, since several of them have distinct wording.
      `_numericBounds()`/`_resolveRef()` in `bin/embed_schema.dart` were
      added to follow one level of `$ref`/`allOf` indirection when reading
      bounds, so the generator keeps working against the de-duplicated
      schema; re-verified the generated `field_constraints.g.dart` is
      byte-for-byte the same as before this schema refactor, and all 47
      `ebc_db` tests (incl. `ProfilesValidator` schema validation, which
      exercises `$ref`/`allOf` resolution through the real `json_schema`

      `schema/bounds.schema.json` split.** Extended generation beyond
      `profiles.schema.json` to cover `settings.schema.json`'s

      schema file, `schema/bounds.schema.json`, holding bounds-only `$defs`

      cross-usage-agreement check needed, since there's exactly one place

      `_profilesFieldConstraintRoles`/`_settingsFieldConstraintRoles` (path-
      walked per file, as before; a property resolving through a `$ref`/

      everywhere, no conversion needed for any of these 9, unlike several
      of the original 18 profile roles). Total generated roles: 27.
      Deliberately still excluded: `ConvertorsState`'s own direct fields
      (`length`/`weight`/`pressure`/`temperature`/`torque`) — these sit one
      level deeper than every other field this generator handles (behind
      `allOf: [{"$ref": "#/$defs/UnitValue"}]` *plus* a nested
      `properties.value` override, not a leaf number property directly),
      and three of them have the unresolved discrepancies below — handling
      the shape and the discrepancies together, later, rather than teaching
      the generator a one-off nested-property case for just these five.
      `AnglesConv.angular_value_mil` (`convertorAngular`) also stays

### Phase 8 — Profiles list/card UX follow-ups (not started)

Surfaced while building/testing Phase 3.5's `.ebcp` import. Not storage-
format work — pure `lib/` UI/UX, filed here since it's directly adjacent to
the profile-card actions Phase 3.5 just touched.

- [ ] **Profile list/cards need a UX rework — open question, not decided.**
      There are currently **two** screens showing profile actions —
      `ProfilesScreen` (`my_profiles_screen.dart`, the main grid editor,
      `ProfileControlTile`) and `ProfilesListScreen`
      (`profiles_list_screen.dart`, a lighter switch-active-profile list,
      `CollectionItemTile`) — with overlapping but not identical actions
      and, per the items below, inconsistent/misleading labeling between
      them. Whether these should merge into one screen, stay two with a
      clearly different purpose each, or something else, is not decided —
      flag for a product decision before touching card layout, not just a
      mechanical fix.
- [ ] **`ProfilesListScreen`'s edit action is mislabeled.** Its
      `CollectionItemTile.onEdit` (`profiles_list_screen.dart:263`) shows
      the generic `l10n.editAction` ("Edit") label
      (`collection_item_tile.dart:47`) but is wired to `_onRename`
      (`profiles_list_screen.dart:99-114`), which only renames the
      profile — not an "edit the whole profile" action. A user could
      reasonably expect "Edit" to open the full profile editor. Contrast
      with `ProfilesScreen`'s `ProfileControlTile`
      (`profile_control_tile.dart:41,55,59`), which already uses the
      correct specific label `l10n.editProfileName` ("Edit Profile Name")
      for the same rename action — `ProfilesListScreen` should match that,
      not invent new wording.
- [ ] **No hotswap "replace weapon" action.** Ammo and sight both have a
      hotswap action sheet (`_onReplaceAmmo`/`_onReplaceSight`,
      `my_profiles_screen.dart`) offering create-new / from-collection /
      import-from-file, replacing the whole sub-message via
      `setProfileAmmo`/`setProfileSight`. Weapon has no equivalent —
      `_onEditWeapon` (`my_profiles_screen.dart:84-98`) only opens the
      in-place edit wizard on the *existing* weapon's fields
      (`Routes.profileEditWeapon`), there's no "swap in a different
      weapon entirely" action sheet. Given `AppStateNotifier
      .setProfileWeapon` already exists (used internally by `_onEditWeapon`
      itself), adding the hotswap action sheet is mechanical once the
      Phase 8 UX decision above is made — but should wait for it, since a
      weapon hotswap sheet's shape (which entry points, collection vs.
      import) is exactly the kind of thing that decision should settle.
- [ ] **Hotswap actions don't warn about data loss.** `_onReplaceAmmo`/
      `_onReplaceSight`'s `replace()` closures call `setProfileAmmo`/
      `setProfileSight` directly on a successful pick — no
      `showConfirmDialog` first, unlike profile *removal*
      (`_onRemove`, `removeProfileContent`), which does warn. Replacing
      ammo/sight silently discards whatever was previously configured on
      that profile (BC tables, zero data, click values, etc.) with no
      "duplicate the profile first" nudge. Should warn and recommend
      duplicating the profile before replacing, mirroring the delete-
      profile confirm pattern (`showConfirmDialog`,
      `isDestructive: true`) — needed for the not-yet-built weapon-hotswap
      action above too, from the start, not retrofitted later.
- [ ] **`ProfilesNotifier.build()` doesn't sanitize on load.**
      Found while testing `.ebcp` round-trip export/import: a profile
      whose `Zero.pressure_h_pa` was a raw proto3 `0.0` (never clamped)
      was sitting in live app state and got faithfully exported as-is.
      `ProfilesNotifier.update()` (`db_provider.dart`) runs every write
      through `sanitizeProfile`, but `build()` — the initial load of
      `profiles.ebcp` at startup — returns `_initial` directly, no
      sanitize pass. A profile saved to disk before Phase 7's sanitize
      gate existed (or otherwise never touched by an `.update()` call
      since) can carry out-of-range/zero-default values indefinitely,
      invisible until something (like `.ebcp` export) surfaces it. Two
      options, not decided: sanitize once in `build()` too (fixes it at
      load time, one line), or leave load unsanitized and keep every
      *consumer* of possibly-unsanitized data defensive (the direction
      `.ebcp` import already took — see the `EbcpValidator` correction
      above). Leaning toward sanitizing in `build()` too, since "state is
      always in-range" is a simpler invariant to reason about than "state
      is in-range except right after cold start" — but not applied yet,
      flagging for a decision alongside the Phase 8 items above.
- [ ] **Navigating to the profiles list isn't discoverable.** The button/
      entry point that takes the user to `ProfilesListScreen`
      (`profiles_list_screen.dart`, the switch-active-profile list) isn't
      obvious from `ProfilesScreen`/Home — surfaced as a usability
      complaint while testing the `.ebcp` import work this session. Ties
      into the same "two screens with profile actions" open question
      above (first Phase 8 item) — likely resolved together, not
      separately.
- [ ] **Standalone ammo/sight import/export (outside a profile) works
      poorly, not really implemented.** Import/export actions scoped to
      just an ammo or sight — independent of any profile — are
      unreliable/incomplete today. Possibly related to the orphaned-data
      question Phase 5 is tackling (old library-style ammo/sight not tied
      to a profile, no home in the new schema) — deferred until Phase 5's
      approach to orphaned data is settled, since that may inform whether
      standalone ammo/sight import/export is even the right shape going
      forward.

### Phase 9 — Web platform support (spike done, real implementation not started)

**Current state, at a glance:**
- Boots, renders Home and Tables, both showing *real computed* ballistics
  (not static/seeded display-only values) — verified live in both
  `flutter run -d chrome` (dev/DDC) and a `flutter build web` static
  bundle served over LAN.
- Nothing persists. Every write (`ProfilesNotifier.update()`, settings
  changes, etc.) still targets `MsgStore`'s `dart:io` `File` — will throw
  the first time a user actually edits anything. Boot-time state is
  seeded fresh into memory every load; a page reload loses all of it.
- `dart_bclibc`'s facade/WASM work published to pub.dev as `0.1.2-beta.2`
  — root `pubspec.yaml` now pins `dart_bclibc: ^0.1.2-beta.2` directly
  (`source: hosted`, confirmed in `pubspec.lock`); the temporary
  `dependency_overrides` (first a local `path:`, then a `git:` pointer at
  the `feat/async-iface-and-wasm` branch while it was unpublished) has
  been removed entirely. `flutter analyze`/`flutter test` (453/453) still
  clean against the published version.
- One **unexplained root cause** left open (concurrent `AsyncCalculator`
  calls hanging) — currently papered over app-side, not actually
  understood at the `dart_bclibc`/wasm level. See the dedicated item in
  "still needs" below.
- **Update — `dart_bclibc` split into two published packages.**
  `dart_bclibc`'s facade/WASM work has since been republished as two
  separate pub.dev packages: `dart_bclibc` (pure-Dart core — bindings,
  unit types, the sync `Calculator`) and the new
  `dart_bclibc_flutter` (Flutter plugin wrapper — bundles the native
  binaries per-platform plus the wasm/`assets/wasm` delivery for web, and
  is where `AsyncCalculator` now lives). Root `pubspec.yaml`'s direct
  dependency moved from `dart_bclibc: ^0.1.2-beta.2` to
  `dart_bclibc_flutter: ^0.2.0-beta.1`; `dart_bclibc` itself is now
  pulled in transitively (also bumped to `0.2.0-beta.1`). This broke
  `ballistics_service_impl_web.dart`'s import of `AsyncCalculator` from
  `package:dart_bclibc/bclibc.dart` (that class no longer resolves from
  there at all) plus carried a stray typo'd import
  (`package:dart_bclibc_/unit.dart`) — both fixed by importing
  `package:dart_bclibc_flutter/dart_bclibc_flutter.dart` (once bare, once
  `as bclibc`), which re-exports everything `dart_bclibc/bclibc.dart` did
  plus `AsyncCalculator`. Re-verified with `flutter analyze` (clean) and
  `flutter build web --debug` (succeeds).
- Everything else below this summary is the detailed log of what broke
  and how it was fixed, plus the full list of what real (non-spike) web
  support still requires.

**Update — a throwaway spike got the app actually booting in Chrome.**
Prerequisite that unblocked this: `dart_bclibc`'s `feat/async-iface-and-wasm`
branch shipped a real WASM engine (`AsyncCalculator`, platform-split via
`async_engine_io.dart`/`async_engine_web.dart`) *and* fixed
`lib/bclibc.dart`'s facade to conditionally export the sync-FFI-only
symbols (`Calculator`, `BCLIBCFFI_*` bindings) only on native, stubbing
them out on web instead of dragging `dart:ffi` into any web build that
merely imports the facade. `ebalistyka` pointed at it via a temporary
`dependency_overrides` in root `pubspec.yaml` while it was unpublished —
first a local `path: ../dart-bclibc` override, then a `git: {url:
https://github.com/ballistics-lab/dart-bclibc, ref:
feat/async-iface-and-wasm}` override so the branch resolved for anyone/CI,
not just this machine's local checkout. **Resolved — the branch has since
been published to pub.dev as `0.1.2-beta.2`**; the override was removed
and root `pubspec.yaml` now depends on `dart_bclibc: ^0.1.2-beta.2`
directly, like any other package.

With that in place, `flutter build web --debug` still failed on four
*app-side* blockers (found by iterating `flutter build web` until clean,
not guessed in advance) — all fixed by conditional-import splits, same
shape as `ebc_db`'s own io/web pattern, no runtime branches:

- [x] `lib/main.dart`'s direct `BcLibC.open()`/`dart:ffi` import and its
      `path_provider`/`ob_migrate` (→ `ob_dump_reader` → `dart:ffi` for
      LMDB) usage → extracted into `lib/core/app_bootstrap_io.dart` /
      `app_bootstrap_web.dart` (conditional on `dart.library.js_interop`).
      Web variant seeds `SettingsData`/`ProfilesData` straight into memory
      (`seedSettings()`/`seedProfiles()`, never touching `MsgStore.load()`)
      instead of opening real files — `path_provider` has no web impl at
      all (throws `UnsupportedError` at runtime, not a compile failure),
      so this sidesteps it rather than fixing it; the migration gate
      always resolves to "no gate" on web (no legacy ObjectBox store can
      exist in a browser). **Known gap left open, not masked**: later user
      edits (`ProfilesNotifier.update()`/`SettingsDataNotifier.update()`)
      still call `MsgStore.save()`, which *will* throw on web once
      something is actually edited — this spike only gets past *boot*,
      it doesn't implement Phase 9's real storage backend (below).
- [x] `lib/core/services/ballistics_service_impl.dart`'s synchronous
      `bclibc.Calculator()`/`BCLIBCFFI_TrajFlag` (undefined on web now
      that the facade stubs them) → new
      `ballistics_service_impl_web.dart`, ported to `AsyncCalculator`,
      selected via a conditional import in
      `core/providers/service_providers.dart`. Sequential `await`s on
      each `AsyncCalculator` call are fine *specifically on web* — the
      web engine is a cached, already-loaded wasm module with no
      isolate-per-call spawn the way native's `async_engine_io.dart`
      (`Isolate.run` per call) has — so this is not a template for
      migrating the native file too; batching multiple native calls
      behind one `compute()` (today's shape) vs. N separate
      `Isolate.run`s (naive `AsyncCalculator` reuse) is a real perf
      tradeoff that needs its own decision, out of scope here.
- [x] `lib/update/update_checker.dart`'s `Abi.current()` (the only
      `dart:ffi` usage in that file — used solely to pick an Android APK
      asset's ABI suffix) → extracted to `apk_abi_suffix_io.dart` /
      `_web.dart`; web variant returns `'_universal.apk'` since the result
      is moot there (see the update-checker UX item below for the actual
      web-side behavior this feeds into). One unrelated debug `Abi.current()`
      print in the same file switched to `Platform.version`.
- [x] **Found and fixed a real, pre-existing bug, not spike-specific**:
      `lib/shared/helpers/is_desktop.dart`'s `isDesktop` checked only
      `defaultTargetPlatform == windows/linux/macOS` — on web,
      `defaultTargetPlatform` reflects the *host OS* (Chrome on this
      Linux box reports `TargetPlatform.linux`), so `isDesktop` was `true`
      in a browser too, and `main.dart`'s `window_manager.ensureInitialized()`
      call (gated behind it) crashed on launch with `MissingPluginException`
      the first time this app was ever actually run on web. Fixed with a
      `!kIsWeb &&` guard. This bug already existed before this session;
      the web spike is just what surfaced it.
- [x] **`checkVersionState()` (`update_checker.dart`) threw uncaught on
      every Home screen load** — `Platform.operatingSystem`/
      `.operatingSystemVersion` (unlike `Platform.version`, which doesn't
      throw) and `getApplicationSupportDirectory()` are both unconditional
      in this function, called automatically from `home_screen.dart`'s
      `_checkIsFirstRun()` on every Home `initState`. Fixed with an early
      `if (kIsWeb) return NewVersionState.none;` at the top of the
      function — there's no installed-version marker file to compare
      against in a browser tab anyway. `checkForUpdate()` (the *manual*,
      button-triggered GitHub-release check in Settings) has the same
      class of problem but isn't auto-triggered, so it's left for the
      update-checker UX item below rather than patched reactively here.
- [x] **CanvasKit defaults to fetching from `gstatic.com`, not the
      bundled local assets** — `build/web/canvaskit/` already ships
      `canvaskit.wasm`/`.js` locally, but the default generated
      `flutter_bootstrap.js` only uses them as a fallback; it prefers
      `https://www.gstatic.com/flutter-canvaskit/<engineRevision>/`
      unless told otherwise. A client with no route to that CDN (an
      offline/LAN-only test device, in particular) hangs on the splash
      screen forever waiting on a fetch that never resolves — even though
      `main()` itself already finished successfully underneath (confirmed
      via `AppStateNotifier: 1 profiles` still appearing in the console).
      Fixed by adding `web/flutter_bootstrap.js` (the officially-supported
      customization point — see the comment in the generated
      `index.html`) that calls `_flutter.loader.load({config:
      {canvasKitBaseUrl: "canvaskit/"}})`, forcing the local assets.
- [x] **`AsyncCalculator` calls from two different screens can hang
      indefinitely if they overlap in time** — reproduced live: Tables
      screen stuck in its loading spinner forever on a cold boot (Home's
      own initial calculation still in flight), but working fine navigated
      to on its own (e.g. after a hot restart, with nothing else
      mid-calculation). Root cause not fully pinned down — read through
      `bclibc_ffi_web.dart` and confirmed every wasm call is a plain
      synchronous Emscripten export with no Worker/`SharedArrayBuffer`
      involved, so true JS-level interleaving mid-call should be
      impossible in principle; the actual mechanism (likely something in
      `bclibc`'s C-side zero-finding/integration state, not the JS
      bridge) needs more investigation on the `dart_bclibc` side before
      calling it understood. Mitigated app-side for now: `Ballistics
      ServiceImpl` (web) serializes every `calculateTable`/
      `calculateForTarget` call through a single `_serialized()` queue so
      only one is ever in flight against the shared engine at a time —
      confirmed this fixes the reproduction (Tables now renders
      immediately on cold boot). This is a safety net scoped to this one
      service instance, not a fix at the shared-engine level in
      `dart_bclibc` itself — a second `AsyncCalculator` consumer elsewhere
      in the app (none exist today) wouldn't be protected by it.

Net result: `flutter build web --debug` succeeds, and `flutter run -d
chrome` boots to Home with a seeded profile, and both Home's and Tables'
calculations render real numbers (not just static seeded data). Not yet
verified: interacting with anything that writes through `MsgStore` (will
throw, per the known gap above) — this was a "does it boot and compute"
spike, not a claim that the app is fully usable on web.

**What Phase 9 itself (the real, shippable version) still needs — the
spike above didn't do this part:**

- [ ] **Storage backend: one key per file, not a new file-based
      convention.** Same two-document shape as disk (`ProfilesData`,
      `SettingsData`, still fully independent — see Doc #8's Core Design), just
      keyed instead of pathed: an IndexedDB object store (or whichever
      key-value API ends up backing it — package choice not made yet) with
      two entries, `settings`/`profiles`, each holding that message's
      "md5+ebcpbuf" bytes exactly as `MsgCodec<T>` already encodes them.
      The wire format doesn't change; only *where the bytes land* does.
      This replaces the spike's "seed in memory, never persist" shortcut
      in `app_bootstrap_web.dart` with something that actually survives a
      page reload.
- [ ] **Abstract `MsgStore`'s file I/O behind an interface**, so
      `lib/`/the rest of `ebc_db` keeps calling `load()`/`save()`/`flush()`
      without caring whether the backing store is a `File` or an IndexedDB
      key — conditional import (`msg_store_io.dart` /
      `msg_store_web.dart` behind a stub, the standard Dart web/io-split
      pattern) rather than a runtime branch, so the unsupported platform's
      implementation isn't even compiled in.
      `openEbcDbStores`'s `File('$directory/settings.ebcp')`/
      `File('$directory/profiles.ebcp')` construction needs the same
      split, or a different entry point on web (no `directory` string to
      speak of for a key-value store).
- [ ] **Not decided yet, needs a decision before implementation**: which
      package/API actually backs this on web (`package:web`'s IndexedDB
      bindings directly, `idb_shim`, `hive`-style wrapper, plain
      `window.localStorage` if the data is small enough — `.ebcp` files
      are currently a few hundred bytes to a few KB, well within
      `localStorage`'s per-origin quota, so IndexedDB's async complexity
      may not even be justified over a synchronous
      `localStorage.getItem/setItem` pair keyed `settings`/`profiles`).
- [ ] **Update-checker UX on web — decided, not built.** The native
      "check GitHub releases, offer to download/install an APK/exe/
      AppImage" flow (`update_checker.dart`, `update_sheet.dart`) doesn't
      make sense on web at all — a browser tab just runs whatever was
      last deployed, there's nothing to "check for updates" from inside
      the page, and there's no file to download-and-run. Decision: on web,
      replace the update-check button/flow entirely with a simple dialog
      listing download links for the other platforms (GitHub releases
      page, Play Store, etc.) — i.e. "get the app" rather than "update the
      app." Not implemented yet — `update_sheet.dart`/wherever it's
      triggered from (`home_screen.dart`, `settings_screen.dart`) still
      needs its own `if (kIsWeb)` branch to swap in this dialog instead of
      calling into `update_checker.dart` at all.
- [x] **`dependency_overrides` in root `pubspec.yaml` removed** —
      `dart_bclibc` published the facade/WASM work to pub.dev as
      `0.1.2-beta.2`; root `pubspec.yaml` now depends on
      `dart_bclibc: ^0.1.2-beta.2` directly (`source: hosted` in
      `pubspec.lock`, no override needed). `flutter analyze`/`flutter
      test` (453/453) still clean against the published version.
- [ ] **Out of scope for this phase, still true after the spike**:
      booting doesn't mean full feature parity. Persistence (above),
      legacy-migration UI (correctly never shown on web, nothing to do),
      and anything else that assumes a real filesystem still needs
      auditing file-by-file before calling web "supported," not just
      "boots."
- [ ] **Final task: deploy to GitHub Pages.** Once the items above land,
      wire a `flutter build web --release` (with the local-CanvasKit
      `flutter_bootstrap.js` fix from the spike above) into a `gh-pages`
      deploy — either a dedicated GitHub Actions workflow (matching the
      shape of the existing `build-*.yml` release workflows) publishing
      `build/web` to the `gh-pages` branch, or an equivalent manual step,
      whichever the team decides on when picked up. This is the last item
      in this phase — everything else above is a prerequisite for this
      being a real, usable deployment rather than a demo.

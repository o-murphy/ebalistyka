# Phase 3 — Riverpod integration + Profiles screen split

## Context

The app currently persists through ObjectBox (`packages/ebalistyka_db`), a
relational entity graph (`Weapon`/`Ammo`/`Sight`/`Profile`/settings
entities, all linked via `Owner`/`ToOne`/`ToMany`). `packages/ebc_db` — a
new, self-contained, fully tested (38 tests) package — replaces it with
two independent protobuf documents (`ProfilesData`/`SettingsData`,
persisted as `profiles.ebcp`/`settings.ebcp`) plus a future share/backup
envelope (`EbcpData`, out of scope this phase). Design and rationale for
all of this already live in `docs/backlogs/8.PROTOBUF_STORAGE_MIGRATION.md`
and `docs/backlogs/8.3.md` — this plan is the concrete, code-grounded
execution checklist for wiring `ebc_db` into the running app (`lib/`) and,
newly in scope this session, splitting the Profiles screen into a Current
Profile screen and a Profiles List screen (today's screen conflates
browsing/picking with viewing/editing).

Confirmed with the user: Phase 5 (legacy ObjectBox → `ebc_db` migration,
via `ob-dump`) is explicitly **out of scope** for this plan and can land
last, right before release — no release ships until it's done, but nothing
here needs to wait for it. **The finalized version of this plan must also
be written into `docs/backlogs/8.3.md`** (as a new "Implementation Plan"
section) as the first execution step, before any code changes — this
mirrors how every other design decision this session has been recorded.

Grounded via two Explore passes (current provider layer; Profiles screen +
UI patterns) and one Plan-agent validation pass that read the actual
current sources end-to-end, including the real `ebc_db` generated proto
classes. Two things that changed as a result of grounding, not guessing:

1. **Naming collision.** Today `settingsProvider` means `GeneralSettings`
   specifically (`AsyncNotifierProvider<SettingsNotifier, GeneralSettings>`),
   with dozens of call sites depending on that exact type — it must NOT be
   reused for the new combined-settings notifier. The new one is named
   `settingsDataProvider`.
2. **`ebc_db` field names are not a 1:1 mirror of ObjectBox field names** —
   `Ammo`'s zero-condition fields moved into a nested `Zero` submessage,
   `ConvertorsState` is fully restructured into nested submessages
   (`UnitValue`/`AnglesConv`/`VelocityConv`/`DistanceConvTargetSize`),
   `UnitSettings` fields dropped their `Unit` suffix. Each extension file
   needs the real proto class read before porting, not assumed.

## Design decisions made while planning

- **`AppStateNotifier` stays `AsyncNotifier<AppState>`** (not converted to
  sync `Notifier`), even though nothing in it is actually async anymore —
  `build()` just returns `AsyncData(...)` synchronously, same adapter
  pattern used for the settings notifiers. This avoids touching the ~10
  files that read `ref.watch(appStateProvider).value`. Consistent with Doc
  #8.3's "keep every existing provider name and base class" instruction.
- **`isReadyForCalculation` stays ammo-only** (today's implementation
  checks `muzzleVelocityMps > 0 && caliberInch > 0 && weightGrain > 0 &&
  lengthInch > 0` + drag-type-specific BC — no weapon field is checked
  today despite `Profile.isReadyForCalculation` delegating to it). Port
  exactly this field list with `hasX()` guards added — don't silently
  expand scope to weapon fields.
- **`Routes.ammoSelect`/`sightSelect` are deleted outright**, not
  repointed. `ProfileControlTile`'s ammo/sight buttons currently hard-push
  those routes with `extra: profileId` — since `MyAmmoScreen`/
  `MySightsCollectionScreen` are gone, the "pick or build" action-sheet
  choice moves inline onto the Current Profile screen (mirrors the
  existing `_onAddTap` weapon-creation flow), pushing
  `Routes.ammoCreate`/`cartridgeCollection`/`bulletCollection`/
  `sightCreate`/`sightCollection` directly — those child routes are
  unaffected by any of this.
- **`settings_screen.dart`'s whole-app Backup/Restore also breaks and
  must be stubbed in the same pass** — found during grounding, not in the
  original scope list. `EbcpService.buildFullExport`/`restoreFromExport`
  feed `ref.read(appStateProvider).value`/`ref.read(settingsProvider).value`
  into old `ebalistyka_db` `*Export` types; once those providers return
  `ebc_db` types this stops compiling. The `restore(...)` methods on all
  5 settings/conditions notifiers exist *only* to serve this restore flow
  (confirmed via grep, no other caller) — delete them outright rather than
  porting, same as the per-profile `.ebcp`/`.a7p` import/export stub.
- **`saveProfile` is removed**, not ported — its only call site
  (`profiles_vm.dart`'s rename flow) becomes a dedicated
  `renameProfile(String uuid, String name)` on `AppStateNotifier`.
- Old `packages/ebalistyka_db` and new `packages/ebc_db` are already both
  declared in root `pubspec.yaml` — no pubspec change needed; the old
  package stays as dead weight for now (retired in Phase 6).

## Post-migration bug fixes (follow-up session)

With Steps 0–9 complete and the full test sweep green (459/459, `flutter
analyze` clean), a critical regression surfaced in live usage: wind and
twist had no effect on calculations, and elevation/windage adjustments on
the Home screen stayed frozen. Root-caused and fixed as follows.

**Root cause.** Proto3 has no way to express a custom non-zero default the
way the old ObjectBox entities could (explicit Dart field defaults, or
sentinel values like `caliberInch = -1.0` for "unset"). Every migrated
field silently defaults to `0.0`/`false`/`''` if never explicitly set.
`ShootingConditions.pressureHPa`/`temperatureC` ended up unset in a
persisted `settings.ebcp` predating an earlier `db_seed.dart` fix this
session — `pressure = 0` drove the native engine's `density_ratio` to
zero, which zeroed the drag coefficient `km`, which killed both velocity
decay and windage together (they share the same drag-force term). This
was invisible to headless tests because every test fixture constructs
fresh `ShootingConditions` with real values — only a live app loading
*already-persisted* broken data hits it.

**Fixes applied**, all following the same two-sided pattern established
here — self-heal already-broken persisted data on read, and stop new bad
data from being written:

- `lib/core/extensions/conditions_extensions.dart`,
  `ammo_extensions.dart` (`zeroTemperature`/`zeroPressure`) — `hasX()`
  presence checks with sane-atmosphere fallback (15°C / 1013.25 hPa)
  instead of raw field reads, so a stale `0.0` self-heals instead of
  producing a physically-vacuum shot.
- `lib/core/models/field_constraints.dart` — added `Constraints.clamp()`.
- `lib/core/providers/shot_conditions_provider.dart` — every `updateX`
  method now clamps to its `FieldConstraints` range before writing
  (write-side validation, not just a read-side patch).
- `lib/core/extensions/ammo_extensions.dart` — added `bc1`/`bc7`
  `hasX()`-aware getter/setters (mirroring `caliber`/`length`/`weight`/
  `mv`) and `sight_extensions.dart` gained `calibratedMag`, previously
  accessed via raw field reads outside the extension layer.
- `lib/features/home/sub_screens/ammo_wizard_notifier.dart`,
  `lib/core/collection/collection_parser.dart`,
  `lib/features/tables/details_table_mv.dart` — fixed the same
  null-vs-zero conflation for `bcG1`/`bcG7`: code was writing an explicit
  `0.0` when the user/JSON left a BC field blank, which marks the proto
  field as *set* with a wrong value instead of genuinely unset.
- `lib/main.dart` — freshly-seeded `SettingsData`/`ProfilesData` are now
  persisted immediately (`_openStores`), not left to whichever code path
  happens to trigger the first mutation. Previously `profiles.ebcp` was
  never written until the user edited something, so a user who closed the
  app right after first launch would silently re-seed a *new* random
  profile uuid on every subsequent launch.
- `lib/features/home/home_vm.dart`,
  `lib/features/tables/trajectory_tables_vm.dart` — added a generation
  counter around `_recalculate()` so a slow, superseded calculation can
  never overwrite a fresher one's result (defensive; not the root cause
  of the reported symptoms, but a real gap found during investigation).

**Verification**: cleared `settings.ebcp`/`profiles.ebcp`, fresh
`flutter run -d linux` launch — no exceptions, both files written
immediately with correct byte sizes, live windage/drag/twist confirmed
non-zero and physically correct via native-engine trajectory sampling.
`flutter analyze` clean, `flutter test` 459/459.
